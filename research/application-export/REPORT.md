# Reusable application-owned capability export — Gate B research (#60 / #75)

**Status:** Research-only recommendation; no accepted public API, transport, credential, implementation milestone or GUI toolkit. **Baseline:** `main` at `a35ac7c9ac9749ff023a72595c6851caee5f4859` (2026-11-21). Owner accepted independent native GUI processes, toolkit-neutral application-facing capabilities, and the *direction* of transport-neutral shared operational semantics; the concrete shared contract and exporter remain open. This report belongs to #60; #75 remains the owner of cross-product identity, readiness, session and authorization semantics.

## 1. Outcome and constraints

A Riesel application written in an independent Cargo project should be able to publish **only selected, versioned application-facing operations** to independent headless, browser or native clients. The application remains the authority for domain state and provider resolution. Publishing a capability must not create a second provider resolver, automatically expose internals, require a GUI or Manager, or execute during static inspection/preflight. A GUI owns its OS process, event loop and transient view state. The intended growth case is more than one domain app, concurrent adapters, multi-client authorization, restarts and future snapshot/subscription integrations; remote access is not implicitly approved.

## 2. Verified existing evidence, versus the new bounded probe

- **#81 (merged, `9979c657`, Linux smoke/validation [44862556171](https://github.com/aschenrot/riesel/actions/runs/44862556171)):** a generated Counter facade over an app-process-owned component accepts a typed client from a different OS process; second client retains state; Observer not exposed. It uses a manually owned listener and remains unauthenticated. It does *not* export the SDK-resolved handle.
- **#82 (merged, `0798a6fb`, post-merge [44863766915](https://github.com/aschenrot/riesel/actions/runs/44863766915)):** a genuine `Application::async_handler`-injected `AsyncCapability<AsyncCounterContract>` can be manually forwarded to an `AsyncRpcHandler` without a second resolver. Per-method arguments, method matching and `CallError::Domain` versus `CallError::Rpc` mapping remain app-owned. The same external typed client interoperates with the two facade modes.
- **#87 (draft, not in `main`, verified head `cf95f71d`, [44875814573](https://github.com/aschenrot/riesel/actions/runs/44875814573)):** a *stale, already-bound external client* can mutate a new OS app process after same-address replacement; a deliberately withheld reply can follow a committed mutation. These are **negative** reference transport properties, not exporter guarantees.
- **Current Todo HTTP** (`examples/todo/src/http/{mod,routes,security}.rs`): an app-owned Axum server integrates domain `Todo`, `Records<TaskData>` and `AsyncTasks`, with explicit routes, HTTP errors, same-origin protection, body limits and graceful shutdown. It works for the web application, but is not a generated typed capability binding, native-attach contract or general caller authentication.
- **New research fixture** (`research/application-export`): an isolated Rust workspace tests one common `ResearchExport` gateway with **Counter** (real SDK-resolved async Counter handle and manual relay) and **Todo** (real SDK-resolved Records, deliberate app-facing `#[capability]`, generated dispatcher). It checks declared-contract selection, identity/generation matching, operation grants, admission/revocation, domain/RPC separation and conservative uncertainty classification. The test *injects simulated identities/generations* and calls a handler directly: it does not implement a secure IPC adapter, live recovery or real OS-client attach. This is a **semantic/policy reuse probe**, not a production-ready exporter.

Rerun exact sources, isolated tests and a source-only non-comment LOC/operation-count report using [README.md](README.md) and [measure.py](measure.py). Source LOC is not an equal-functionality performance/quality benchmark; use it only to expose *where* repetition accumulates. Never equate the Todo HTTP route count with a capability operation count.

## 3. Same target, four competing mechanisms

| Criterion | A. Generated facade component | B. App-authored HTTP (Todo) | C. Manual resolved-capability forwarder | D. Bounded reusable app-owned exporter |
| --- | --- | --- | --- | --- |
| Source of interface contract | Existing generated `#[capability]`; a **public facade** must be authored | Rust domain + app-authored HTTP request, response and route contract (not generated Riesel capability) | Existing generated contract and typed resolved handle | Reuse `#[capability]` and SDK resolution; explicit public selection, **no second schema** |
| Selection/state ownership | New facade component/instance may duplicate state **if it is not bound to the app's real services** | App-supplied `Todo`/Records state; domain stays authoritative | Real SDK-resolved handle, no second resolver | App exports intentionally selected resolved handle/domain facade, no auto-exposure; app remains authoritative |
| Per-operation mapping | Generated dispatcher after implementing trait; facade methods still need to delegate to application domain | Each app writes routes, validation, response/error mapping and HTTP UX | Each method needs argument decode, dispatch match, `CallError` mapping; three Counter arms in #82 | Reusable lifecycle and grants; **per-operation forwarding still needed** for SDK-resolved client handles without generator support |
| Listener + task lifecycle | Application manually binds, announces and stops test host | App server, worker budgets, shutdown and origin logic manually authored | Same as A plus per-operation relay | Scope-owned listener/connection policy *could* centralize admission, owned stop and readiness; not proven in the new probe |
| Discovery/attach | Research-only stdout address, no trusted descriptor | Browser-specific authority/origin and optional port | Research-only stdout address | Propose trusted per-session descriptor, explicit attach; cannot reuse a port as app/session identity |
| Session/restart | In-process handles guarded; external client **not** fenced across process replacement | HTTP backend lifetimes, storage revisions; no common external generation | Same unfenced external transport | Research gate rejects mismatched generation **only because simulated caller passes it**; server-enforced/restart correctness must come from #75 |
| Authorization | Explicit contract route ≠ caller authorization | Same-origin browser request defense ≠ general local peer authentication | No caller authentication in current loopback fixture | Explicit per-principal/per-operation grants can be reused, but trusted principal and enforcement before network dispatch are unimplemented |
| Errors/unknown effects | Generated typed domain/RPC split; loss of reply is still ambiguous | Todo maps domain/Storage failures into HTTP status; transport may lose reply | Correctly preserves `CallError::Domain` vs `CallError::Rpc` | Gateway can centralize policy errors and classify ambiguous command replies, not promise exactly-once |
| Snapshots/reconnect | Normal typed query and deliberate rebind | Todo list/read/revision handling is app-specific | Normal typed query and deliberate rebind | Reattach only with a fresh authorized generation, then query authoritative snapshot; no auto-replay |
| Future events/subscriptions | New declared interface/methods or protocol work | SSE/WebSocket or app-specific channels | More handwritten stream plumbing | Keep a separate versioned/authorized stream grant and snapshot/resume policy extension; do **not** implement a generic broker now |
| Long-term migration | Public facade per app can accumulate wrapper boilerplate and state ownership confusion | Existing Todo browser routes should remain supported; no forced migration | Manual forwarding scales with operation count | Potential one shared adapter policy and generated forwarding; migration is additive and opt-in, not a replacement for special-purpose HTTP |
| Technical/research risk | Duplicate component state or implicit internal exposure | Different domain HTTP APIs remain legitimate | Session errors can be accidentally converted into domain errors | Security/epoch/transport work is substantial; premature SDK syntax or token issuance could lock in unsafe invariants |

**Other material options:** A reverse proxy, toolkit-owned transport, socket registry or common Manager daemon moves listener/bootstrap mechanics but does not remove authorization, ownership or session validation. A generic reflection-based JSON call gateway would lose Rust typed method guarantees or require schema-based dynamic dispatch; nothing in the current cases justifies it. These mechanisms should remain possible adapters, not mandatory exporter architecture.

## 4. Two-application boilerplate and semantic reuse

**Counter:** published `AsyncCounterContract` is already versioned and the SDK handler resolves the real typed handle. The manual app-facing relay has three operation dispatch arms (`value`, `add`, `label`), two payload structures plus an empty-input structure, a codec helper and the domain/RPC preservation helper. The earlier common host additionally binds OS-assigned loopback, announces, starts and stops the host, and manually routes the interface. In the new fixture, those operation arms **still exist**; the reusable gateway removes duplication only in app/interface/epoch policy and grants. A production-grade typed relay generator is a real remaining candidate, but belongs to an accepted public API decision.

**Todo:** `Todo` already contains authoritative create/read/update/delete behavior and revision checks; the existing browser HTTP adapter maps app-specific routes, errors and browser security. The research fixture deliberately declares a *small different app-facing* `TodoPublic` contract (create/count) and uses its generated dispatcher over SDK-injected `Records<TaskData>`. The same gateway works without implementing Counter-specific policy. This is **not** proof that Todo HTTP can be replaced losslessly: it does not export the full CRUD/revision/pagination/HTTP-origin semantics, and deliberately avoids duplicate schema by treating `TodoPublic` as a new boundary rather than rewriting the existing HTTP API.

**Measured and not measured:** `measure.py` computes nonblank/non-comment source LOC per comparator and the exact number of selected method match arms and HTTP route handlers from this branch. The Counter-generated/manual pair is closely comparable as a narrow 3-operation interface; the existing Todo HTTP API and the Todo 2-operation export are *not functionally equivalent*. There is no valid percentage boilerplate reduction, throughput/latency number or full two-application production cost claim yet. The main measurable result is **one shared policy wrapper for two distinct SDK dependency shapes** while retaining app-authored domain API and Counter manual dispatch.

## 5. Responsibilities — the proposed bounded exporter

**Exporter should own (if accepted):** opt-in mapping from named app-facing interface to a contract + SDK-resolved service or explicit domain facade; validation of exported contract/API shape and allowed operations; scope-bound listener, owned connection/request budgets, shutdown/drain and diagnostic provenance; per-session external descriptor and pre-dispatch validation; adapters for approved local transport(s); explicit caller authentication hook and fine-grained policy enforcement; consistent transport/policy/domain/unknown-outcome error envelope; readiness evidence that *this* interface is authorized and callable; no mutation replay.

**Application code keeps:** defining a deliberate public facade and its behavior; choosing which operations/principals are allowed; handling domain validation/business authorization and revisions; ownership of persistent state, snapshots and mutation side effects; existing provider selection and lifecycle; opt-in exposure/start policy; browser-specific HTTP semantics and GUI rendering when chosen. The exported facade is **not necessarily identical to the internal provider contract**. Component provider identity or the discovery address is never promoted to public application identity.

**#75 owns shared invariants, not the exporter implementation:** an externally verifiable app identity/build provenance; unique non-reusable session generation bound to real runtime lifetime; authoritative interface publication/attach; authenticated principal and authorization rules including same-UID local adversaries; callable-readiness state; operation error categories/unknown effect policy; correlation between runtime teardown and externally observable session expiry. None can be substituted by a serialized `SessionToken`, self-reported principal string, PID, port, provider metadata or `RIESEL_READY`.

**#60 owns after #75 acceptance:** application declaration and selection mechanics, adapter ownership and scope, attach path used by independent native client, contract-specific forwarder generation, migration guidance, and validation with an actual GUI loop. #59 Manager registration/OS ownership is optional; #68 developer tooling can consume verified descriptors but does not issue runtime epochs by implication. #83 execution scheduler remains independent.

## 6. Provisional developer-facing shape — not accepted Rust API

```text
Application::async_handler(|resolved_counter, export_scope| async move {
    export_scope.publish("ui.counter", AsyncCounterContract, resolved_counter)
        .allow("gui", ["value", "add"]) // application policy, not trust proof
        .serve_until_session_stops().await
})
```

This is an **intent-only sketch**, not code that compiles, not a recommendation to add an `ExportScope` parameter yet. The boundary may instead be a separate optional builder call or an app-specific adapter over an accepted shared operational service. Keep `#[capability]` as the single contract source, allow composable explicit public interfaces, preserve async and sync SDK modes where suitable, and require no exporter in headless-only applications. No SDK syntax, transport, new crate, static configuration file or public provider descriptor should be frozen from this sketch.

## 7. Security, lifecycle, versioning and error requirements

1. **No implicit publication:** inspection/preflight and definition generation are pure with respect to endpoint startup; only the running owning app session starts the exporter. Only named app-facing contracts/operations are exported; internal Observer or Storage cannot be reached unless deliberately authorized.
2. **Trust before dispatch:** a binding to the right contract/version/epoch is necessary but **not sufficient**. Resolve and verify *actual peer* identity using an accepted local/remote policy, including same-UID adversary rules, and enforce authorization on every operation/stream. A simulated `Principal` from the research fixture is NOT a credential.
3. **Generation/restart fencing:** server derives/validates current generation and rejects stale descriptors and in-flight old attachments **before** new-session mutation. There must be no implicit rebinding after same-address restart. Invalidating an in-process `SessionToken` alone is insufficient. Generation must not be reused accidentally.
4. **Callable readiness:** distinguish declared, resolved, listener-bound, auth-checkable and callable from a real authorized client. Riesel provider-ready lines do not attest application export readiness.
5. **Unknown mutation outcomes:** a lost reply can follow a committed side effect. Preserve `CallError::Domain` vs transport errors, report `outcome unknown`, avoid any automatic replay. Query/refetch and application domain revision keys are a recovery mechanism, not exactly-once.
6. **Lifetime and bounds:** application session owns listener and all handler tasks. Closing an independent UI does not stop backend. On app stop, deny new admission and drain/cancel owned requests per the accepted runtime contract; distinguish unknown in-flight external effects. Set bounded frame/request size, pending calls/connections, deadlines and cancellation; trust policy must be enforced before allocating expensive work.
7. **Evolution and reconnect:** publish independently versioned capability contracts and externally verifiable descriptor generation. After restart, explicit fresh attach then authoritative snapshot. Document compatible/breaking changes, revoked grants, and multiple-client behavior. Preserve optional future snapshot+events extension with authorization and resync cursor/backpressure semantics; no broker/delivery guarantee is included.
8. **Platforms:** Linux-first candidate UDS + private runtime directory deserves a threat-modelled experiment. OS filesystem mode and same-UID peer credentials are not authorization against malicious same-user processes. Windows named-pipe ACL/security and native host tests require separate evidence before parity claims. Current TCP is unauthenticated; do not ship it as a protected export.

## 8. Implementation-ready acceptance scenarios (research gate; not authorized tasks)

| ID | Given / when | Required observation |
| --- | --- | --- |
| E1 | Counter app uses an already SDK-resolved typed handle; independent typed client attaches | Client sees same authoritative state as in-process app, no second resolver or duplicate schema; unselected Observer rejected |
| E2 | Todo app uses SDK-resolved Records and a deliberate public CRUD/revision-aware contract; independent client attaches | Same source domain semantics and persistence across frontend disconnect; no forced replacement of existing browser HTTP |
| E3 | App starts with no UI, then independent GUI/client connects, exits, reconnects | App remains alive; fresh authorized attach and snapshot succeed; GUI does not own domain state |
| E4 | GUI closes during pending write; app process crashes/restarts on identical address | Old client/descriptor cannot mutate new generation; new trusted client attaches; old write may report unknown and is never implicitly resent |
| E5 | A same-UID untrusted process, wrong app/interface/version, revoked grant, and malformed/oversize frame attempt connection | Each rejected **before** domain dispatch, with appropriate observable error/diagnostic, without privileged descriptor leak |
| E6 | App provider is ready but exported interface not yet authenticated/callable | Readiness remains non-callable; authenticated fresh probe becomes callable only after app handler and listener policy are active |
| E7 | Client loses response after successful committed Counter/Todo mutation | Typed result is unknown rather than domain failure; explicit fresh snapshot/revision reads reconcile state; no duplicate write |
| E8 | Multiple clients with separate permissions call query and command concurrently | Per-principal operation restrictions and resource budgets hold without cross-client ticket reuse; authorized query remains available |
| E9 | App shutdown or whole-session recovery occurs with pending export requests | Listener/tasks are session-owned, new admission denied, partial commands classified, fresh epoch required; provider teardown order respected |
| E10 | Published interface version or deployment changes; client uses outdated contract | Unsupported binding fails early, accepted new version is explicit; no silently inferred ABI compatibility |
| E11 | One independent native GUI process uses chosen toolkit with an event loop | Attach/detach does not block event loop; keyboard/focus/error visibility and Linux smoke verified; domain state remains in backend |

**Fixture coverage now:** E1 partial (in-process policy + existing #82 two-process), E2 partial (small create/count, in-process only), E4/E7 negative external transport demonstrated in **#87** and semantic gate simulated here, E5 simulated policy subset. All other E-rows are unproven. No claim of an authenticated implementation or public API is made.

## 9. Decision recommendation and irreversibility audit

**Recommend investing in a bounded reusable app-owned exporter** because the current examples show real duplication of listener/authorization/lifecycle policy, and a naive generated-provider facade can accidentally fork state. However, **do not approve a public exporter mechanism yet**: the new isolated policy fixture has not demonstrated authenticated external attach, real session fencing, authoritative readiness, whole-session recovery or eliminated Counter per-method forwarding. Completing those tests depends on #75's cross-product invariants and a production-capable adapter, not on a particular GUI toolkit.

**Best next order:** (1) complete #75 identity/epoch/auth/callable-readiness/unknown-effect decisions and positive external tests; (2) from this research, compare a generated resolved-handle forwarder against a hand-authored domain facade and an optional generic wrapper using both full Counter and CRUD/revision-aware Todo; (3) approve a bounded exporter API/transport only on actual two-process evidence and migration cost; (4) implement native GUI attachment and toolkit-specific UX as a separate #60 delivery slice. If #75 favors independent adapters and a shared model but no exporter, preserve this gateway as evidence and use adapters without creating a permanent crate.

**Bias audit:** the working manual facade must not bias toward an indefinitely handwritten per-app design; the existence of a generic research gateway must not bias toward a new core crate or mandatory daemon. The critical irreversible choices are wire authentication/epoch binding, exported-contract publication semantics, version compatibility and client retry behavior—not the provisional Rust builder syntax or test-only folder structure.

**Disposition requested from owner:** review/revise the boundary and evidence, not merge or freeze public APIs. Keep #60 and #75 open. Do not change roadmap, create implementation issues, select GUI toolkit, or merge this research PR without explicit authorization.
