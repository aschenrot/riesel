# #158 — Internal source-qualified observation slice

**Status (22 November 2026):** Verified internal, source-qualified implementation for the accepted #158 scope. This is **not** a public observer API, authenticated application exporter, protected Manager control, or production service. **Contract owner:** [Shared operational semantics #75](../../docs/product/riesel/operational-contract.md); implementation evidence and closure rationale belong to [#158](https://github.com/aschenrot/riesel/issues/158).

## Implementation, ownership and reason for reusing a type

A small internal, in-process `riesel_app::operational_observation::ObservationSnapshot` represents **facts rather than one global readiness state**. It is compiled under the existing `internal-publication` test feature; the normal public `riesel` SDK exports no new observation type, port, schema, capability, app exporter, authenticated client or management command.

- **Riesel runtime**: `RunningApp::internal_operational_observations()` samples the existing supervisor/task checks and returns the **actual** session-token generation, plus specific versioned `ResolvedCapability` bindings issued after provider metadata/contract validation. A verified local or managed binding is a binding fact, **not** an attestation that a public app interface exists, that the OS attempt was authenticated, or that future calls will work. If current checks fail, no success is projected.
- **Actual SDK application entrypoint (third runtime fact, not a readiness shortcut)**: the existing per-session `AsyncTasks` owner records the typed/low-level SDK Rust entrypoint's lexical phase: `NotEntered`, `Executing`, then `Left`. The SDK invokes its feature-gated marker **only at the actual application callback**, after provider composition, and for async lifecycle applications **after all start hooks have succeeded**; it drops the guard **before stop hooks**. It does not label a provider handshake or a start hook as handler-ready. The `ObservationSubject::ApplicationEntrypoint` is emitted by the runtime with `SdkEntrypointNotEntered`/`SdkEntrypointExecuting`/`SdkEntrypointLeft` evidence, bound to the *same* runtime `SessionToken`, not an application-authored epoch. A snapshot of any earlier phase becomes `Stale` immediately after a transition (or session invalidation), even within the nominal five-second maximum. A foreign session witness is rejected, a second concurrent/late entrypoint admission is rejected and an uninstrumented adapter may not claim that its listener proves the handler was entered. Even `Executing` attests only **code running**: it does not attest a published interface, functioning business operation, verified peer or grant. This remains test-feature instrumentation, not a public Handler API or automatically published metadata.
- **Application's own listener**: `ObservationSnapshot::local_listener()` accepts a caller-supplied runtime-session reference and a numeric bound loopback socket with an explicitly named interface. Its scope is explicitly `AdapterReferenceOnly`, **not** an independently runtime-attested epoch; the runtime-owner constructor alone marks `RuntimeIssued`. An adapter could otherwise mint a token and falsely claim to be the runtime, so a later external consumer must independently verify the relationship. It attests that the participating adapter **observed a bind at that instant**. It is not a live perpetual socket probe, authenticated remote readiness or any application operation grant.
- **Local OS launch owner (second independent snapshot scope)**: `ProcessOwnerSnapshot::sample()` delegates exclusively to the existing `riesel_manager::ProcessRegistry::observe_owned_attempt()`, whose retained actual `Child` handle is the authority for **one registry-local OS child attempt**. `ObservationSource::ProcessOwner` and `OwnedChildHandlePolled` distinguish this from `RuntimeIssued` application generation and adapter listener evidence. The internal-only `OwnedAttemptEvidence` contains a weak lease to its exact registered child; dropping, stopping or re-registering the same `ProcessKey` invalidates old evidence instead of treating reused names/IDs as the same attempt. Poll-observed `Running` / `ExitedSuccess` / `ExitedFailure` phases are about the child at that instant, not its app handler readiness, a verified executable artifact, privileged Manager target, or authorized client. A failed/unavailable registry lookup produces `Unknown`, never evidence that the child stopped. The owner does **not** invent a Riesel application generation or durable PID/OS identity; the two snapshot types are deliberately **not** a globally atomic observation. The same bounded monotonic freshness applies.
- **Application-owned operation outcome evidence (fourth independent fact source)**: `AdapterOperationSnapshot::report()` is feature-gated, on-demand, and reports exactly one bounded named adapter operation using the actual active Riesel session reference. `AdapterOperationEvidence` distinguishes `RejectedBeforeDomainDispatch` (only after this adapter has confirmed no domain dispatch), `DomainConfirmedSuccess` (domain-reported success, not guaranteed client delivery), `DomainConfirmedFailure` (typed domain failure, not necessarily absence of earlier effects), `AdmittedReadResultLost` (read result **unavailable**, not an uncertain mutation or empty read), `AdmittedReplyLost` (admitted **mutation** reply may have dispatched/committed, **outcome unknown**) and `ConfirmedPartialRequiresReconciliation` (known sub-effect with incomplete multi-stage workflow). They map to separate `OperationDisposition` categories. Evidence is **app-adapter reported**, `AdapterReferenceOnly` generation, never independent remote verification, external client authorization, durable transaction/Manager receipt or exactly-once execution. Operation names are bounded to 128 ASCII identifier bytes; a report contains no raw arguments, errors, token, client identity or history. Monotonic five-second staleness and session revocation apply. Events are not a stored journal, hot-path graph/Query observer or implicitly retriable command.
- **Unavailable authorities**: the runtime and app adapter emit `AuthorizedApplicationOperation` and `OsLaunchAttempt` as `Unsupported`, because they lack authoritative external principal/authorization evidence or an OS launch-attempt owner. The process owner now independently attests **only** its retained child OS status, not app interface callability. Absence of a named subject is `Unknown`; failed local checks also produce `Unknown`, not falsely “stopped”. A previously observed fact becomes `Stale` if its real owner/scope is revoked, replaced or its snapshot exceeds a five-second in-process monotonic-clock age.
- **Bounds, privacy and evolution**: maximum 64 facts/snapshot, each subject-label (including configured instance names) limited to 128 UTF-8 bytes; overflow and malformed labels are explicit errors, not silent truncation. Facts contain only typed provenance, versions, planned instance identity, numeric loopback addresses, and a nonsecret runtime generation. No raw error strings, credentials, HTTP request content, OS labels, process command lines, persisted history, serialized publication or background observer thread. Snapshots are on demand, not queried on each graph/ECS/Query frame. No cross-process/global clock ordering is inferred.

## Real consumers and negative evidence

1. **Headless Counter**: the existing genuine managed Counter crash/recovery fixture checks versioned provider binding as `Runtime`-issued and `SdkEntrypointExecuting` as actual handler evidence. A real typed Counter increment confirms its domain effect and the participating app adapter records `DomainConfirmedSuccess`; after actual same-PID whole-app recovery, the old event is `Stale`, and an old-generation ingress request is rejected before the successor provider mutates. A new session owns a different runtime-issued generation. The test adapter still reports public authorized application operation **Unsupported**, not callable merely because the internal Counter succeeds. `probe_internal_publication.py` requires both the original recovery and the outcome-provenance marker.
2. **Persistent Todo**: the real Todo/SQLite SDK app creates a typed task, binds an OS-assigned numeric loopback TCP listener, performs an actual TCP connection and records a separate `ApplicationAdapter` listener observation. The socket bind is `Observed` but an externally authorized app operation and verified OS attempt remain **Unsupported**; the listener snapshot becomes `Stale` at SDK shutdown. A fresh SDK session opens the same persisted task.
3. **Actual registry-owned process attempts**: the existing `ProcessRegistry` launches real child executables and observes `Running` and `ExitedSuccess` using its own child handle. Previous running evidence expires when exit is sampled, or after actual stop/removal and same-key reuse; absent key is `Unknown`. The runtime still cannot independently attest `OsLaunchAttempt`.
4. **SDK entrypoint boundaries**: real Counter handler callbacks in session A and recovered B attest `SdkEntrypointExecuting`. A Todo async handler attests the same while writing SQLite and binding loopback. A separate actual SDK module-hook fixture observes `NotEntered` inside `on_start`, `Executing` across an `await`, `Left` in `on_stop`; prior snapshots stale immediately upon each transition. The handler merely running does not prove interface readiness.
5. **Source-qualified operation outcomes in two app shapes**: the actual managed Counter test distinguishes a confirmed typed mutation in session A and rejected-before-effect old request against recovered B, with the former report stale. In Todo, an exhausted real `AsyncTasks` blocking admission budget returns `Unavailable` and proves the domain closure never executed; a separate actual committed in-memory Todo mutation whose result oneshot is dropped returns HTTP `503 outcome_unknown` even though one task exists. A persistent SQLite multi-stage Todo workflow confirms a create succeeded, then receives a definitive revision-conflict domain failure during completion: the app reports the compound workflow as **partial/reconciliation required**, re-reads the actual record, and opens a new session to prove the create was not automatically replayed. No single error category overwrites the other's authority, and no new durable event store is installed.

6. **Actual independent Todo HTTP client / adversarial browser-header proof**: `examples/todo/tests/http.rs::independent_client_proves_route_reachability_not_protected_identity_or_stale_session` executes the **unchanged** SDK-based `todo_http` in a separate Linux OS process, with the test-runner HTTP client under the **same observed UID but a different PID**. One real GET establishes only that the selected route handled **that request**. A wrong Host or missing Origin returns 403 and creates no record. A non-browser same-UID client then forges the exact permitted numeric Host, Origin and `Sec-Fetch-Site: same-origin`, performs a **real SQLite mutation** through the app, and reads it back: **Host/Origin/Fetch Metadata and reachability do not authorize a protected client**. A transient client disconnect leaves the server running. SIGINT and an actual waited OS child exit prove the **old owned attempt** ended, while a refused connect proves only that the old TCP endpoint was unavailable **at that instant**, not general app death. A separately started SDK Todo process opens the same SQLite database while the old port is deliberately held by the test (preventing accidental port reuse); a stale Host is denied by the adapter and the saved record is readable through its fresh endpoint. This proves no externally authenticated application/session identity, protected individual grant, cross-process epoch or production exporter. The source categories remain: child exit from the test's owned `Child`, route result from the independent client, and a trusted-local test adapter's browser-origin policy. Never collapse these into a universal `callable` bit or infer that old-session HTTP effects can be safely replayed.

Previously integrated, **not reimplemented**: executable-vs-passive inspection `tools/xtask/src/smoke/operational.rs`, API `503 unavailable` vs `outcome_unknown` and real committed write after lost reply [#171](https://github.com/aschenrot/riesel/pull/171), browser uncertain mutation/reconciliation [#179](https://github.com/aschenrot/riesel/pull/179), graph/nested observers and linked Query model authority. The model does not overwrite or serialize any of these owners' existing state.

### Deliberately unsupported; no hidden dependency or false readiness

- The internal OS-child owner attests one retained process attempt, **not** a verified installation, protected artifact owner, persistent privileged process authority, or Manager command.
- SDK `SdkEntrypointExecuting` attests user code entry, **not** an operation-specific readiness or authenticated interface. A Todo `TODO_HTTP_READY` line and a successful GET establish a bound listener and response only. The separate same-UID non-browser client *successfully mutated actual SQLite through forged browser headers*, proving that this trusted-local browser adapter is **not** a protected individual-client boundary.
- There is **no** independently authenticated published app/interface/contract version and external operation grant in these producers. The accepted semantics return **Unsupported** for that fact, not an invented callable status. Deliberate secure app capability publication belongs to [#60](https://github.com/aschenrot/riesel/issues/60) and its separate security acceptance; the executed #149/#151 same-UID counterexamples rule out casually treating UID or selectable AppArmor labels as trusted individual-client identity.
- A universal cross-workspace developer launcher or source-/freshness-qualified **generic** CLI is a separate pending [#68](https://github.com/aschenrot/riesel/issues/68) product/tooling decision; existing app-local inspection and independent Cargo smoke are retained without accepting that mechanism. Protected OS targets, authorization and durable mutation receipts belong to [#59](https://github.com/aschenrot/riesel/issues/59).
- Per-adapter `AdapterOperationSnapshot` is one bounded, on-demand event, **not** a transaction journal, recovery ledger, or authoritative remote receipt. The already integrated Todo [#201](https://github.com/aschenrot/riesel/pull/201) read/mutation classification prevents claiming an unavailable read is an uncertain write. Any uncertain mutation requires explicit authoritative state reconciliation; no exactly-once guarantee or automatic retry is offered.

**Acceptance boundary:** #158 can be completed for its **already supported internal observation and failure projection scope** without implementing #60, #59 or #68. The established #75 choice is shared transport-neutral semantics with product-specific authorities/adapters, not a mandatory observer daemon, public transport/schema, or a second Riesel scheduler.
