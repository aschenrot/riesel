# #138 — Record Query interface conformance comparison

**Date:** 2026-11-22. **State:** evidence and **interface recommendation for owner review**, not an accepted API or an implementation specification. The [accepted product direction in #138](https://github.com/aschenrot/riesel/issues/138#issuecomment-7073259869) is an **optional shared typed Query semantic foundation with domain/provider-controlled execution**. [PR #150](https://github.com/aschenrot/riesel/pull/150) integrated this outcome into the authoritative product definition. Selecting a record Query interface was **explicitly deferred**.

## Same application tasks — no candidate-specific favorable scenario

**T1 — Typed read-only consumer.** An app declares registered Rust model `TaskData` (field types and model identity) and a bounded selective read, without a Storage writer or permission to invoke mutations. Generated inspectable schema must include the model. Deny unsupported query operators and untrusted remote access. This applies to a browser-facing read-only service, not permission for arbitrary external browsers today.

**T2 — Typed read/write consumer.** The Todo app creates/revises a record then queries the **same logical dataset** with immediate read-your-writes. One application should not have to maintain two independent provider selections just to use one authoritative dataset. Preflight rejects incompatible linked selections before construction; session/endpoint checks reject stale or inauthentic managed/external bindings. A valid lifecycle `depends_on` edge alone is not an owner relation.

**T3 — Separate authorized query-only consumer.** A query application may consume a shared data owner without acquiring mutation methods. Model permissions, caller identity, chosen consistency/freshness profile and provider visibility must remain enforceable. Its existence does **not** imply every reader shares the writer process: an explicitly attested proxy or stale replica may be supported in a later profile.

**T4 — Scale and correctness under change.** Memory and SQLite implement the same supported field/model/type semantics: exact `u64`, UUID normalization, absent-versus-null, deterministic advertised ordering, bounded work (not just row counts), explicit incomplete/error outcomes, invalid cursor/schema/owner/session fencing, and honest non-snapshot behavior. A scratch SQL index or reference scan is not a production proof.

**T5 — Evolution.** Preserve Storage v2 compatibility, explicit provider ownership and offline migration guarantees. Query profiles/contract versions and physical indexes must evolve without silent startup DDL, cross-domain forced execution or an unsupported general-purpose query engine.

## Design families after discovery — one common comparison

These are **architectural packaging families**, not a forced shortlist or names for approved APIs. Hybrid designs remain eligible when they satisfy T1–T5.

| Realization | T1 read-only model and least privilege | T2 read-your-writes / SDK | Evolution and provider work | Critical deficit |
| --- | --- | --- | --- | --- |
| **Separate read-designated record facet** + shared typed semantics, co-exposed with Storage v2 for linked use | A distinct contract can avoid mutation methods; first-party model-only SDK registration **not implemented**; external authorization still required | Two runtime requirements; requires a declared, fail-closed same-logical-data authority relation or a verified composite selection | Independent query version/profile; retains v2; provider-native execution still unimplemented | Authority pairing, typed read-only model registration, declared consistency and related error semantics need a coherent first-party solution |
| **Unified evolved Storage contract** with query and write operations | One contract still offers mutation operations unless real operation authorization or a separate attenuated read facet is introduced | One provider selection intrinsically directs reads and writes to one handle; straightforward schema registration | Version/migration coupling across all v2 consumers; physical work still owned by Storage | A pure Rust read-only wrapper over a writable RPC contract is **not** least-privilege authorization |
| **Model-/authority-scoped facet bundle (discovered hybrid)** | One declared logical model/data authority can offer only a read facet to the read-only app; enforcement still required | One provider/authority selection may yield separately versioned read and write facets under a declared consistency relation, instead of two unrelated aliases | Retains distinct contracts and v2, with a new resolver/schema relation and model-only registration path | **Not implemented or tested:** must prove preflight+runtime co-authority and avoid turning a relationship into an unverified logical provider ID or duplicating #75 identity |
| **First-party composite typed handle** combining read facet and writer | Can hide multiple handler parameters; can expose read-only projection | Experiment proves it can still resolve separate stores; must embed or declare an independently verified relation | SDK convenience layered over either underlying architecture | Alone it is **not** a storage contract, a model-only declaration facility, an authenticated principal or an owner proof |
| **Domain-owned typed read methods + shared validation/semantic helpers** | Application/domain can expose a dedicated read-only service with its own authorization | Can keep domain authority and avoid extra universal resolver pairing | Requires repeated domain provider implementations for the same registered-record selective semantics unless a common record adapter is added | Does not itself deliver a common operable record-query interface, error/budget/cursor guarantees; still a valid specialization where common interface is unnecessary |
| **Separate analytical/federated engine** | Can expose independent read service after actual access/identity controls | A copy or separate executor must define snapshot/staleness and write authority | High flexibility for accepted analytical/join workloads | No accepted first-record need; large owner/consistency/cost and runtime responsibilities, not solved by choosing an upstream planner |

**Decision pressure:** The separate read facet is currently attractive for **independent version evolution, v2 preservation and a genuinely narrower operation surface**. The unified contract is attractive for **one-handle data affinity** but cannot claim read-only access with a client-side wrapper alone. The composite helps **ergonomics only**, not authority. An authority-scoped facet bundle may combine independent read permission with one logical provider selection, but its schema/resolver and trust guarantees are unimplemented; it must be compared on the **same tasks**, not treated as automatically superior. The shared semantic foundation is compatible with all these realizations, and no generic engine is required for the supported registered-record outcome.

## Minimum interface semantics that should be accepted before implementation

1. **Model declaration independent of mutation authority.** A typed read-only app can register a model and the read capability without declaring `RecordStoreContract` or physical Storage v2 model bindings. Schema must identify which query requirement is authorized to read which model, without assuming all readers are writers.
2. **Explicit logical data authority relation.** When read-your-writes is required across query/write requirements, application schema and deployment selection declare their relation and intended consistency. Validate before side effects and at runtime using the actual provider owner/session. A named managed instance, endpoint, provider metadata pin or in-process session token alone does not establish authenticated remote authority.
3. **Least-privilege operation and model scope.** Read-only method shape must have a real enforcement boundary; do not equate a Rust wrapper, a `#[query]` annotation, or a loopback address with authentication/authorization. External model visibility is denied until the relevant #75/#60 profile is accepted.
4. **Typed, bounded, truthful results.** Define exact supported operator/type profile, distinguish missing/present-null and invalid operands, make results/cursors model/predicate/schema/authority/session-bound, distinguish incomplete from empty, and fail on unadvertised or over-budget query work. Do not silently promise live mutable-sort snapshots.
5. **State and evolution.** Provider-owned Memory/SQLite execution, stable compatible Storage v2 behavior, versioned Query profile and opt-in/index-maintenance with separate offline ownership and rollback guarantees. Do not require a universal planner or a read-through replica initially.
6. **Developer-facing coherence.** First-party SDK handlers and explicit builders generate the **same** validated schema and provider plan. Read-only model usage should be as straightforward as `Records<T>` without granting writer capability; read/write apps should not manually duplicate alias configuration or invent identity names.

No Rust trait/API name, on-wire expression grammar, state-token format, permission credential, physical index schema or mandatory provider process topology is approved by these invariants.

## Recommendation and owner decision still required

**The shared typed semantic foundation is accepted independently of public interface packaging.** For the first **linked** registered-record realization, prefer testing **a read-designated facet attached to a single declared model/data authority**, potentially using a general facet-bundle relationship, before accepting any public shape. It must support first-party **typed read-only model registration, least-privilege operation exposure, and fail-closed owner/consistency verification**. A composite SDK abstraction is potentially useful to eliminate manual double alias selection, not a substitute for that relation. Evaluate against the unified/attenuated Storage alternative before declaring the facet accepted.

**What would change this preference:** If a clean, auditable owner relation plus model-only declaration is materially harder or leaks more authority than a real operation-scoped attenuated Storage interface, prefer that unified/attenuated design. If initial supported users only need domain-owned reads, don't force an independent general record-query endpoint merely for a Query label. If secure remote reader replication becomes first-release scope, the #75 identity/authorization and consistency proofs are necessary *before* accepting that placement.

**Next decision:** Owner chooses whether to accept (a) **a read-designated linked facet with first-party model/authority-scoped binding**, (b) a **unified/attenuated record Storage alternative with equivalent least privilege and model authoring**, or (c) **defer** for a concrete outstanding architecture question. A generic, shared authority relation must be justified independently of this Query example and must reuse rather than duplicate #75's trust guarantees. Continue using #138 as the specification decision record; no duplicate research Issue or production implementation Issue is warranted before that decision.
