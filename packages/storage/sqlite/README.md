# SQLite Record Storage provider

An explicit, reusable **linked-only** `RecordStore` v2 implementation. The constructor `sqlite_storage_provider(path, models)` is side-effect-free; the database is opened by the existing fallible local factory during runtime startup.

- SQLite WAL with `synchronous=FULL`, explicit local-disk path and one cooperating lifetime owning provider per file (Linux-verified exclusive sidecar lock).
- UUID-ordered records, 8-byte `u64` revisions, transactional optimistic update/delete, bounded pages, and 64 KiB JSON payloads.
- Requires authoritative model definitions and rejects incompatible persisted model metadata on reopen rather than silently migrating data.
- Database open, permission, lock, schema and corruption errors fail without falling back to MemoryStore.

**Not provided:** runtime-managed Storage hosting, automatic or online schema migrations, a complete operator maintenance workflow, network-filesystem sharing, transparent retries or OS/power-loss certification. Engine-level forced-process-exit research lives separately in [PR #29](https://github.com/aschenrot/riesel/pull/29). See the [accepted architecture](../../../docs/product/riesel/durable-record-storage-architecture-proposal.md).

**Cached-schema write safety:** Existing linked providers verify the entire persisted model registration and physical format within each SQLite create/update/delete transaction. A provider whose cached model set is no longer the stored model set rejects writes without mutating records. This does not prevent legacy/uncooperative writers, does not itself invoke the separate explicit migration engine or replace cooperative lifetime database ownership, and does not establish safe online schema evolution. See [issue #44](https://github.com/aschenrot/riesel/issues/44) and [Stage 6 specification #41](https://github.com/aschenrot/riesel/issues/41).

### Cooperative owner boundary

The linked provider now acquires an exclusive standard-library file lock on a **persistent** `<database>.riesel-owner.lock` sidecar before SQLite opens. It holds the file handle through provider shutdown and refuses a second cooperating owner. Relative/parent-symlink paths resolve to one canonical database path. On Linux, unsupported direct file symlinks, hardlinks, writable-by-group/others database directories/files/lockfiles and detected lock/database identity changes fail closed. The lockfile remains after shutdown and must **not** be deleted or replaced during operation.

This is an operator-controlled, trusted-local-filesystem mechanism. It does **not** prevent pre-upgrade Riesel binaries, arbitrary SQLite clients, adversarial same-user directory mutation, or races against malicious pathname replacement. The already-open provider detects a visible replacement at its next operation but this is not a cross-process tamper-resistant lease. Stop old binaries and block their restart before any maintenance; do not infer this automatically. Windows file identity/path-policy validation remains a manual pre-release gate. See [ownership implementation #48](https://github.com/aschenrot/riesel/issues/48) and the [accepted offline migration architecture](../../../docs/product/riesel/sqlite-offline-migration-architecture.md). Ownership alone does not initiate backup or migration; those are separate, explicitly invoked offline maintenance operations.

### Explicit offline backup (Stage 6)

The low-level `SqliteMaintenance::open_existing(path, source_models, budget)` is a **separate, explicit maintenance action**. It acquires the same cooperating lifetime owner as `SqliteStore`, refuses an active provider, and audits the existing format-v1 database, exact source schemas, UUIDs, revisions, JSON records and SQLite integrity without initializing or changing source records. `backup_to(destination, budget)` creates a consistent independent SQLite `VACUUM INTO` snapshot at a unique pending path, validates every copied row against the source, checks caller-supplied record/byte/file ceilings, syncs the backup file, then publishes without overwriting an occupied destination. The temporary path is not reported as a valid backup.

**The snapshot alone does not perform a migration, constitute a safe restore procedure or prove host power-loss durability.** The bounded independent backup/restore gate [#49](https://github.com/aschenrot/riesel/issues/49) is accepted for the cooperating single-host Linux scope. Explicit typed execution and registered target invariants are implemented under [#50](https://github.com/aschenrot/riesel/issues/50), which remains in final acceptance review; the operator preview/consent/recovery workflow [#51](https://github.com/aschenrot/riesel/issues/51) remains outstanding. The caller must ensure a trusted local filesystem and an operator-controlled legacy-binary shutdown/restart barrier; `integrity_check` alone does not validate arbitrary application-level JSON references.

### Explicit offline restore (bounded format-v1 scope)

`SqliteMaintenance::restore_from_backup(source_snapshot, snapshot_models, retain_current_at, budget, RestoreAuthorization::DiscardPostSnapshotWrites)` is a **separate, deliberately authorized operation**, never part of application startup. It requires exclusive cooperative ownership of both the current valid format-v1 database and the verified snapshot. Before changing records, it validates both, retains an independent verified copy of the current state at an unoccupied path, then uses SQLite's built-in backup/restore API to restore the snapshot through the destination database connection. It compares the restored records to the snapshot, consumes the maintenance instance, and returns the retained pre-restore artifact for inspection.

**Data-loss boundary:** the caller explicitly acknowledges discarding writes made after the source snapshot. Restoration of a **physically corrupt or unreadable destination is not yet supported**; the valid-current-schema preflight must succeed. An error following the backup API copy may leave the target state uncertain; the retained pre-restore copy is required for explicit operator recovery. This does not prove host power-loss safety, uncooperative writer exclusion, automatic legacy-binary termination or Windows parity. The verified initial backup/restore gate is accepted in [Issue #49](https://github.com/aschenrot/riesel/issues/49); broader recovery and the deliberate operator workflow remain separate [Issue #51](https://github.com/aschenrot/riesel/issues/51) concerns.

### Backup/restore operational limits

The offline owner is **cooperative** and cannot exclude uncooperative SQLite clients. A pinned independent WAL reader test verifies that snapshots include newly committed rows rather than only main-file pages. Copying the .db file alone while WAL is active remains unsupported.

The SnapshotBudget limits source-file size, record count, raw JSON bytes, published snapshot size, the combined observed SQLite `-wal` / `-shm` sidecar footprint and elapsed time. Maintenance refuses oversized or nonregular sidecars before opening or copying, rechecks before restore mutation and after snapshot comparison, and retains its original no-overwrite behavior. The sidecar ceiling is a preflight measurement, not a reservation or a promise against uncooperative writers. A positive `max_elapsed` limit is shared across restore preflight, verified pre-restore retention, page-stepped SQLite copying and post-copy verification. SQLite progress callbacks interrupt long statements, and timeout before backup publication leaves no completed backup. These checks are cooperative and cannot preempt blocked OS I/O; failure after a completed restore copy requires examining the retained pre-restore copy. Before a backup or restore, an additional OS filesystem-capacity query checks for at least **twice the declared maximum snapshot size** available on the relevant destination volume (the backup-output volume and, for restore, the database volume). Missing capacity or overflowing reserve arithmetic rejects the operation before copying or mutating records. On Unix, a destination directory without owner write permission is also refused before creating a pending backup. This is deliberately conservative: callers should choose realistic declared ceilings. Unix uses `statvfs`; Windows uses `GetDiskFreeSpaceExW`, pending its manual release gate.

This preflight is **not reserved space** and does not prove that a real disk-full condition, SQLite temporary files, WAL growth, other processes consuming space, or I/O interruptions can never exhaust capacity after the check. It does **not** reserve capacity against future WAL/shm growth, guarantee a hard wall-clock deadline during blocked I/O, or establish host-crash durability. Operators must provision independent backup and pre-restore retention storage plus SQLite journal/WAL headroom, and prevent legacy processes from restarting. Without those conditions, maintenance must not be authorized. Linux additionally tests a kernel-enforced per-file write limit during `VACUUM INTO` in an isolated process; it verifies that a rejected partial snapshot is not published and leaves source records intact. This is a controlled OS write failure, **not** actual filesystem ENOSPC, a guarantee against interruption after publication, or a power-loss test. Invalid-archive and conservative capacity checks remain separate preflight evidence.

On Linux, a separate subprocess also exercises a kernel-enforced per-file write failure during the **actual maintenance restore operation**, after a valid independently retained pre-restore snapshot was published. It checks that the restore reports failure and that the target and retained pre-image reopen with the pre-restore records. This is a controlled `RLIMIT_FSIZE` failure rather than true filesystem ENOSPC; it does not certify post-commit faults or power-loss recovery.

Restore targets an **existing healthy format-v1 database**, not physically corrupt database repair. A post-copy validation failure may leave its state uncertain, requiring inspection of the retained pre-restore snapshot through a separate authorized recovery operation. SQLite integrity checks do not validate application-level JSON relationships. Windows remains a manual pre-release gate.

### Typed model evolution preview and explicit offline execution

The explicitly constructed `ModelEvolution` plans an unchanged set of persistent model names using Rust-derived historical and target `ModelDefinition` values. `transform::<Old, New, _>(...)` requires matching persistent model IDs and source/target Rust definitions; missing or duplicate transforms, model additions/removals and unsupported shapes fail. The maintenance-only `preview_evolution` validates all stored source records, deliberately evaluates registered Rust transforms against target schemas, rejects revision overflow and target size/budget violations, and returns affected-row and projected JSON byte counts. It reads through one SQLite snapshot and **does not mutate the database or create an upgrade backup**. Transformers must be deterministic and must not produce external side effects. The effective preview deadline is the shorter of the requested evolution limit and snapshot audit limit, shared across SQLite integrity checking, row validation and transformed rows. A SQLite progress callback interrupts lengthy SQL statements; it cannot preempt blocked OS I/O or a blocked user transformation callback.

The independently verified backup/restore prerequisite [#49](https://github.com/aschenrot/riesel/issues/49) is complete **for its cooperative offline Linux scope**. Preview never executes or grants permission for a later mutation. The explicitly authorized, internal offline engine below is a separate invocation; operator preview identity/approval and operational launch/stop workflow remain outstanding in [#51](https://github.com/aschenrot/riesel/issues/51).

### Application-level cross-model invariants

`ModelEvolution::invariant(|records| { ... })` registers deliberate checks against the complete **proposed target state** inside the same SQLite `IMMEDIATE` transaction, before commit. The restricted `EvolutionRecords::get(model, uuid)` and `for_each(model, callback)` expose schema-validated records with checked UUID and revision formats. Arbitrary SQL and mutation are not exposed. A validator can ensure a `note.task_id` refers to an existing `task`; failed checks roll back all changes while retaining the independent recovery snapshot. Preview remains read-only and **does not certify post-transform cross-model invariants**. Callbacks must not perform external side effects or block indefinitely; only cooperative deadline checks are possible.
