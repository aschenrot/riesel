# Stage 6 — Accepted offline SQLite model migration contract

**Decision: accepted 2026-11-20 by the project owner in the Riesel development conversation, following [specification Issue #41](https://github.com/aschenrot/riesel/issues/41).** This is an architecture and product-scope decision, **not** a claim that the migration facility has been implemented or that its operational guarantees are verified. Implementation is tracked separately under the [delivery process](../../project/delivery.md).

## Outcome and supported boundary

Riesel must support a deliberate change to a linked SQLite application's Rust-derived `RecordStore` model shape without silent data loss or a second handwritten schema. The first supported deployment is **a single local host with a trusted operator and a controlled local filesystem**, with **one cooperating provider owning a database file at a time**. An explicit offline maintenance operation performs the change while regular application providers are stopped.

The existing `RecordStore` capability v2, `Records<T>` user-facing CRUD API, SQLite format version 1, UUID identifier format, full `u64` revisions, transactional write fence and fallible linked-provider startup remain unchanged unless a separate accepted contract explicitly requires a change. A JSON model-shape change alone must not increment `PRAGMA user_version`.

## Accepted guarantees and implementation constraints

1. **No implicit upgrade.** `SqliteStore::open`, provider registration, application inspection and `App::preflight` never perform migrations. Normal startup rejects unknown or incompatible persistent model definitions. A distinct maintenance command/workflow must have an explicit **preview** (no source mutations) and a separately authorized **execute** action. No silent fallback to MemoryStore.
2. **Authoritative typed schemas.** Developers author immutable historical and current Rust model types deriving `RieselModel`, with the *same persistent identity* for an evolved model, and deliberately authored source-to-target transformations. Maintenance derives both schema sets from these types; no duplicate JSON/SQL schema manifests. A full **exact byte comparison of all persisted model names and serialized definitions** against the supplied source schema is required before execution. Both source and target model sets must be complete and validated.
3. **Initial transformation scope.** Only **non-destructive updates to existing named models** using explicit transformations (or a deliberately approved identity transform for metadata-only changes). No automatic inferred defaults, field renames, lossy conversions, model deletion, model renaming, repartitioning, or physical SQLite table changes. Unknown changes fail closed and need a new accepted extension. Unchanged model records are preserved.
4. **Identity and concurrency.** Preserve every record UUID and untouched-model revision. For every record in a changed model, even metadata-only evolution, **increment the eight-byte big-endian `u64` revision once** as an explicit stale-client fence. Abort on overflow, malformed identifiers/revisions, inconsistent model metadata or invalid source/target JSON; no wraparound or reset. Validate all source records before transforming, all resulting records against the target, and any explicitly registered application-level cross-model invariants.
5. **Whole-operation atomicity.** Under a single bounded SQLite `IMMEDIATE` write transaction, verify exact source metadata, transform and revalidate affected records, update record revisions and model metadata together, then verify target state before commit. Any error before commit must abort the transaction; no partial migrated database is acknowledged. An interrupted transaction follows SQLite's supported rollback behavior, **not** a promise against host power loss.
6. **Cooperating owner exclusion.** Normal linked providers hold an **exclusive lifetime ownership lock**; maintenance acquires the *same exclusive ownership identity* from before backup through final validation and commit. Contenders fail without modifying the database. Implement and test path/alias, symlink/hardlink, owner-lock pathname replacement, permission and process-exit cases. Restrict to a controlled local directory and supported filesystem; reject unverifiable ownership scenarios. A simple replaceable lockfile is not enough by itself.
7. **Legacy rollout barrier.** Pre-fencing binaries and direct SQLite writers cannot be made to honor a newly introduced cooperative lock. **The operator must stop them and prevent their restart**, using deployment/service controls outside Riesel, before maintenance is authorized. No claim of automatic discovery or isolation of such processes. Unsafe or unverified rollover aborts; automatic/online upgrades are excluded.
8. **Verified backup before mutation.** Create a consistent, **independent** snapshot using supported SQLite mechanisms, refusing an occupied/unwritable destination. Verify `integrity_check`, on-disk format, exact source model metadata, and a complete old-schema record validation/reopen before transaction execution. Retain a usable pre-mutation snapshot. Do not copy the main `.db` file alone while WAL is live. Backup retention and cleanup must be explicit and failures must not trigger transformation.
9. **Recovery and downgrade.** A failed pre-commit transform leaves the original database and retained snapshot; restoration is a **separate, explicitly authorized offline action**, after verifying the retained backup, using the same owner exclusion. Its procedure must document source/target validation, replacement and filesystem/WAL syncing assumptions and the **loss of any writes committed after the snapshot**. No automatic post-commit rollback or downgrade is implied.
10. **Finite operational envelope.** The maintenance tool must enforce declared, testable budgets for record count/bytes, elapsed operation time and required disk/WAL/backup headroom, and fail with actionable errors before attempting unsupported work. Define supported local-filesystem conditions and verify simulated interruption, permission/backup corruption and low-capacity paths. All untested OS/filesystem/device/power-loss outcomes are exclusions, not inferred durability promises.

## Non-goals and exclusions

No remote/managed provider migration, concurrent online upgrade, distributed ownership, malicious same-user file tampering protection, arbitrary legacy processes that ignore the lock, network filesystem, generic SQLite DDL framework, automatic downgrade, transparent retry or unlimited-size migration. Windows support remains a **manual pre-release validation gate** until tested and separately accepted. Production reliability still requires independent security, observability and release gates.

## Implementation order and gates

The architecture is **accepted** but each phase must meet its own verification before it is considered delivered:

1. **Provider lifetime ownership and operational boundary:** establish canonical database and stable lock identity, enforce cooperative exclusion on every normal provider open, prove no preflight side effects and cross-process release/failure behavior. Document old-binary rollout requirements. Existing transaction-local write checks remain defense in depth.
2. **Offline backup/restore contract:** provide validated, retained snapshots and a narrowly controlled restore workflow with tests for corruption, occupied output, WAL consistency, source-model identity and failure paths. Work may proceed independently of phase 1 until integrated execution.
3. **Bounded migration engine and typed authoring:** source/target schema verification, deliberate transforms, revision fencing, full-record/cross-model validation and one transaction with injected rollback/overflow and resource-limit tests. Integration depends on accepted owner and backup contracts.
4. **Explicit operator workflow and end-to-end reliability:** preview and separately authorized execute; fail-closed reopens, observed migration, interrupted/unsupported rollback cases, release documentation and Linux checks on the exact merged revision. No production claim before these pass.

If exclusivity, backup viability or finite resource limits cannot be established for a supported environment, **do not run a migration**. Reassess the contract through a new decision rather than weakening its guarantees silently.
