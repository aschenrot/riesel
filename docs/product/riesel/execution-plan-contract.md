# Riesel — Execution Plans, Scheduling and Inspection

**Status:** Accepted product outcomes and architectural invariants (2026-11-21; optional domain-owned nested read-only observation accepted 2026-11-22 in [#146](https://github.com/aschenrot/riesel/issues/146#issuecomment-7073454321)); **headless plan/binding, bounded graph execution, domain/fixed-step admission, read-only *outer* live observation, **trusted-local optional read-only nested observation**, owner-confirmed effect prefixes and local cooperative outer admission control implemented; independent graphical inspector/editor, external authorization and nested control outstanding**. The owner accepted the bounded direction in [specification #83](https://github.com/aschenrot/riesel/issues/83#issuecomment-7063096674), based on [research PR #84](https://github.com/aschenrot/riesel/pull/84) and its [35 passing research tests](https://github.com/aschenrot/riesel/actions/runs/44887680499). Research-only structs, JSON documents, schedulers and examples are **not** approved public APIs or interoperability formats. This contract states required outcomes, boundaries and testable invariants, not a frozen mechanism.

**Partial authoring-source decision (#111, 2026-11-22):** The owner [accepted option C](https://github.com/aschenrot/riesel/issues/111#issuecomment-7074722751): shared validated execution semantics, **one explicitly authoritative semantic authoring source per executable plan**, continued Rust-first authoring, and future support for document-owned visual plans. This establishes the source-of-truth *architecture*, not a document format, export/authorization method, editor API or completed visual-authoring implementation. The [bounded production-plan adapter tests in draft research PR #169](https://github.com/aschenrot/riesel/pull/169) passed on [Linux CI 44985812166](https://github.com/aschenrot/riesel/actions/runs/44985812166); research code and JSON types remain non-normative. The remaining #111 choices are still open.

## Product outcome

A Rust application developer can **describe and validate executable operation relationships, inspect a plan without running operations, execute it headlessly, observe authoritative progress, and cooperate with supported pause/advance/resume safe points**. The execution model supports both event-driven/async applications and fixed-tick simulation boundaries without requiring an ECS, window, daemon or particular GUI toolkit. Optional graphical inspection presents the *same* plan and execution state. Editing executable graphs is a **long-term direction** for a deliberately bounded set of registered operations. The shared-validation, single-authoritative-authoring-source direction is accepted; legal edits, source transitions, binding/publication rights, format compatibility and executable round-trip rules remain a separate specification before implementation.

A headless-only application remains a complete supported application, not an incomplete graphical project.

## Responsibility and authority

| Layer | Responsibility and authoritative owner | Prohibited conflation |
| --- | --- | --- |
| Application definition and capability requirements | Existing SDK/`AppSchema` and the application author | Not an executable operation graph or a process installation |
| Provider catalog and deployment | Existing provider resolver/preflight and chosen provider instances | Not a general scheduler; an operation may consume an already-resolved capability but must not select providers again |
| Application session, tasks and lifecycle | Existing runtime and its owned task/provider/process scopes | Not replaced by an execution-plan controller or second supervisor |
| **Execution plan** | Application-authored, validated description of logical operations, relationships, triggers and applicable constraints | Not executable arbitrary Rust source, a provider dependency DAG, or an untrusted app's verified identity |
| **Plan authoring source (#111 direction)** | One expressly authoritative source of the plan's *semantic definition* at a time: Rust-authored or document-owned; both converge on the same Riesel validation and execution semantics | A read-only projection or visual client cannot silently claim to be a second author, editor or publisher. Source authority and runtime mutation permission are distinct |
| **General graph runner** | A reusable Riesel-owned coordinator for eligible **Riesel-owned** operations, under the existing session | Not universal ownership of all nested domain scheduling, OS processes, native threads or external side effects |
| Executor/operation adapter | Invokes supported registered Rust operations, typed capability handles or explicitly delegated domain work | Does not expose every internal capability to another process |
| Domain coordinator | Authoritative owner of the domain's **internal** tick/frame/system schedules and resources when that boundary is delegated | Riesel cannot separately admit the same inner tick/system while the domain also owns it |
| Optional nested observation owner | Same delegated domain coordinator, optionally publishing a **read-only** typed/domain-specific view plus a minimal parent-correlation/snapshot/loss envelope | This view neither schedules work nor changes the outer graph's authoritative state, terminal outcome or confirmed effects |
| Observer/controller | Reads authoritative plan/state/snapshot and requests supported cooperative controls through the owning boundary | A lossy trace is not the state store; a UI, CLI or remote client is not an independent scheduler |

**One admission/control authority per boundary.** Riesel may admit an outer operation (which in turn invokes a domain-owned frame) or, when explicitly supported, admit distinct outer tick operations. A domain's internals remain under its declared owner. Every presented boundary must identify whether it supports pause, step, resume or only observation; unsupported system-level/native preemption is reported, not simulated. `RunenECS` is an independent possible domain integration, not a required dependency of Riesel.

## Plan construction, inspection and identity

- Validate operation IDs, dependencies, cycles, eligibility rules, declared triggers, supported access constraints and registered executable bindings **before** admitting work. Rejected plans must not run a partial prefix just because some operations are valid.
- Preserve a stable logical plan identity and an **immutable semantic revision** for each executing run. An execution observes the exact accepted plan; a new edit cannot silently alter a running revision. Application-authored executable bindings use supported Rust/capability registration; publishing a manifest alone is not permission to execute arbitrary code.
- An execution address contains at least the owning application/session generation, plan identity/revision, run identity and operation identity/attempt. A session restart or republished plan cannot be mistaken for the old run. Exact persistence, global allocation, signatures, hashes and serialization formats are **not yet selected**.
- Machine-readable plan inspection and current-state snapshots must be available to headless clients. Static inspection must not execute plan operations or create provider instances; obtaining metadata by **launching untrusted Rust code** is not passive or guaranteed safe.
- Keep presentation-only graph layout/editor state distinguishable from semantic plan changes. The **accepted source-of-truth principle** is one explicitly designated authoritative authoring source per plan (Rust code or an editor-owned document), with both paths validated and bound against the same execution semantics. **V2 additionally accepts separate immutable semantic and presentation revisions, deliberate source-authority handoff, and conditional stale-write protection**. The precise compatible source-conversion mechanism and layout rebase/version format remain to be specified before editor implementation.
- Declare supported execution classes (one-shot, event-driven, fixed-tick, and any later admitted policies) with explicit clock/admission semantics. Do not claim generic determinism, real-time deadlines, fully typed data transfer or automatic hot updates merely because a DAG is valid.

## Authoritative state, results and control

- Runtime state must distinguish **pending/eligible/running** activity from terminal completion, cancelled work, known failure and an **outcome-unknown** state when a command may have executed after dispatch but the reply was lost. A specific API may use a richer result type instead of adding one status enum variant; the semantic distinction is mandatory.
- Track **confirmed committed effects separately from terminal classification**, including partial success before cooperative cancellation or failure. A cancellation request cannot roll back a committed tick, remote mutation or prior side effect. A disconnected or timed-out observer must not report a missing response as proof of nonexecution.
- Dependent success-only operations cannot advance on unknown/cancelled/failed prerequisites as though they completed. A supported failure policy must define blocked/skipped/terminal results and what authoritative reconciliation is available. No automatic retry of uncertain mutations or exactly-once execution guarantee follows from this architecture.
- Controls are **cooperative**, fenced to the current execution/session and dispatched to the single declared owner at the requested operation/domain safe point. Boundaries that cannot be safely paused/stepped fail explicitly; Riesel will not suspend arbitrary synchronous Rust, GPU operations or OS threads.
- Trace/event delivery may be bounded and lossy. Loss/overflow must be detectable and consumers must be able to **resynchronize from authoritative state**. The trace stream must correlate events to their plan/run/node/attempt without inferring revisions from an observer's local clock or untrusted strings.
- Resource and access declarations guide eligibility but do not prove Rust alias/borrow safety for opaque callbacks. Native thread-affine or `!Send` state stays with its owning executor/domain unless separately proved safe; a shared graph format does not imply automatic cross-thread or cross-process portability.

## Optional domain-owned nested observation (B + F; trusted-local reference implementation delivered)

**Product decision:** [specification #146](https://github.com/aschenrot/riesel/issues/146#issuecomment-7073454321) accepts **optional read-only domain-owner-published observation** (B) with a small reusable correlation/snapshot/loss envelope and **versioned domain-specific typed capability views** (F). This is **not** a public Rust trait, serialized/wire format, ECS interface, universal debugger, generalized recursive graph or export mechanism. The existing outer-only `DelegatedFrame` remains correct and sufficient for authors who do not opt in.

**Authority and composition invariants:**

1. **Separate sources of truth.** Riesel publishes its validated plan/run/attempt and outer operation state through the existing `GraphRunObserver`. A participating domain separately publishes authoritative inner state and its own internal work IDs/sequence. The observer composes a *correlated view*, not a second scheduler; it never invents internal tick/system nodes or equates outer `Completed` with a domain's full internal effect ledger.
2. **Full correlation, independently fenced lifetimes.** A nested observation binds to exactly one Riesel parent application session generation, validated plan identity and immutable revision, graph run, outer operation ID and its authoritative attempt (including an attempt retained after terminal), **plus** a domain-issued owner-instance generation/epoch (and supported domain identity). These addresses must not silently alias after a plan republish, run/session change, domain owner replacement or an operation reattempt. A domain epoch is local correlation and revocation state, **not** proof of a remote principal. Parent identity derives from the authoritative runner/dispatch owner, not untrusted strings or UI-constructed attempt numbers.
3. **Small shared semantics, specialized payloads.** The common projection identifies source domain/owner, parent binding, availability/unsupported state, payload or view version, owner snapshot revision/high-water mark, event cursor and detected loss/resync requirements. Domain-specific ECS systems, simulation ticks, pipeline stages and other details remain **independently versioned** and typed under the owner. Consumers must handle unknown versions or unadvertised finer-grained facilities explicitly. Reusing versioned Riesel capability contracts is allowed where appropriate; the provider catalog alone does **not** publish or authorize independent application readers. No fixed universal inner node schema, mandatory ECS, shared serialized bytes or provider selection source is imposed.
4. **Authoritative resynchronization and bounded delivery.** A domain publishes a coherent owner-local snapshot independently of an **optional**, bounded and possibly lossy diagnostic/event stream. A consumer can detect gaps/overflow/discontinuity or owner-generation change and re-read the authoritative owner snapshot rather than reconstructing missing effects. The retained event budget, cursor scope, snapshot consistency, version mismatch behavior and resource costs must be explicit and finite in implementations. Snapshot and outer graph state are *separately sampled*: no global total order, shared transaction, global wall-clock or atomic two-owner snapshot is implied.
5. **Effect truth and uncertain outcomes.** Inner owner-confirmed partial commits may remain visible after outer cancellation, failure or a lost callback reply, without redefining the already observed outer `Cancelled`, `Failed` or `OutcomeUnknown` terminal classification. A domain's later snapshot is not authority to retroactively increment an expired `GraphEffectRecorder` confirmed prefix. Post-attempt reconciliation, durable mutation idempotency/replay, automatic retry and exactly-once guarantees require separately accepted semantics.
6. **Optional local readers, no newly granted controls.** The first supported implementation boundary is trusted **in-process/headless read-only** attachment. A client detaches without stopping the session or its domain owner; closure, domain restart and session invalidation are observable without retaining a stale mutating handle. The observation mechanism cannot expose `&mut World`, move a `!Send` resource across threads or acquire independent domain scheduling authority. Nested pause/step/resume and external reader authorization are **not** included; unsupported controls continue to reject rather than translate `RieselDomainTicks` into domain-owned `Tick` or Bevy/RunenECS system steps.

**Implementation/evolution gates:** A coherent initial SDK slice must preserve `GraphRunObserver` and `GraphRunController` outer semantics; support one optional domain-owned read-only projection, local versioned domain payloads and loss-aware resnapshot, and verify the same parent/epoch/cancellation/unknown outcomes against **real Bevy ECS, real RunenECS and a non-ECS domain coordinator**. Engine-specific native stepping, presentation plugin rendering, performance policies, transport/export, authenticated independent process access and post-attempt reconciliation remain separable future design gates. The comparator [research PR #148](https://github.com/aschenrot/riesel/pull/148) is evidence only (11/11 isolated Linux tests, [Actions 44978929227](https://github.com/aschenrot/riesel/actions/runs/44978929227)); its actor protocol and fixtures are **not** selected SDK implementations. The first trusted-local Rust API and its explicit implementation limitations are documented in the [session-owned execution runner](execution-runner.md) and delivered in [#153](https://github.com/aschenrot/riesel/issues/153) / [PR #155](https://github.com/aschenrot/riesel/pull/155). This does **not** freeze an external serialization/wire contract, approve authenticated cross-process exports or change the owner-routed controls decision. In particular a cursor must distinguish independent attachments to separate graph operations even when a domain owner generation is reused; typed payloads must be detached owner-immutable snapshots rather than mutable aliases.

## Security and lifecycle integration

The scheduler operates **within** the existing runtime session and honors provider teardown, task cancellation and whole-session recovery. A new session invalidates old controls and handles. The runner cannot become another provider resolver, application launcher or Manager. Independent process/GUI control needs authorization, version and session semantics coordinated with [shared operational research #75](https://github.com/aschenrot/riesel/issues/75), [Manager #59](https://github.com/aschenrot/riesel/issues/59), [native GUI #60](https://github.com/aschenrot/riesel/issues/60), and [developer tooling #68](https://github.com/aschenrot/riesel/issues/68); none is a blanket prerequisite for local/headless execution tests.

A generation number, TCP loopback address, matching local OS user or provider readiness announcement is **not sufficient authentication** for privileged operations. The accepted direction does not automatically approve external control endpoints, credentials, deployment manifests, distributed execution, persistent execution history, replay or a general broker. Refer to the existing [runtime lifecycle](runtime-lifecycle.md) and [async execution](async-execution-contract.md) contracts for current shutdown and uncertain-RPC limits.

## Optional interfaces and visual authoring

**Graphical inspection is accepted as an optional product outcome**, consuming the same versioned plan, authoritative snapshots and loss-aware trace as an SDK/CLI client. It may use an independent interface process, but no toolkit, frontend transport or Manager UI has been selected. It must never be the sole place execution correctness is implemented.

**Accepted #111 architecture direction (option C):** Both Rust-authored and future document-authored visual execution plans shall be representable through Riesel's **shared validated semantic execution model**. Each logical executable plan must identify **one authoritative authoring source for its semantic definition at a time**; two independently editable definitions cannot both act as the plan's authoritative meaning. Rust-first and GUI-free authoring remain first-class. A document-owned plan is a supported future authoring path, not a requirement to serialize or reverse-engineer arbitrary existing Rust code. Importing, inspecting or rendering a code-owned plan does **not** transfer authoring authority; moving between authoring sources requires an explicit, validated handoff with no silent loss of executable semantics. This authoring-source rule does **not** by itself establish who may install, publish, execute, replace, or authorize a plan from an external process.

### Accepted revision and source-transfer architecture — V2 (#111)

**Owner decision:** [V2 accepted, 22 November 2026](https://github.com/aschenrot/riesel/issues/111#issuecomment-7075163935) after [V1/V2/V3 comparison](https://github.com/aschenrot/riesel/issues/111#issuecomment-7074845779). This establishes the **semantics and ownership invariants** below; it does **not** freeze a public document format, storage provider, CAS token, distributed transaction, publisher credential or live-upgrade API.

| Subject | Accepted authoritative behavior | Boundary / unresolved mechanism |
| --- | --- | --- |
| **Semantic execution plan** | An identified logical plan has immutable, revisioned executable semantics: exact registered operation identities/versions, nodes, control dependencies, triggers, constraints and any separately accepted future S3 typed-value edges. Execution/run/attempt observations bind the exact semantic revision. | Owner-issued revision and verification/provenance policy must be specified; the existing in-memory `PlanRevisionCatalog` is not a durable publisher. |
| **Presentation/layout** | Separate *non-executing* layout identity/revision, anchored to a particular logical plan and semantic revision; layout changes affect only visual coordinates, labels and presentation grouping. | Layout cannot set executable dependencies, operation bindings, triggers, resource/domain constraints or value edges. Unknown nodes, incompatible anchors or stale layout versions must be reported; rebase is explicit and validated. |
| **One semantic authoring owner** | Each plan has one authoritative Rust or document authoring source at a time. Exporting a read-only Rust plan/description does not authorize or convert it to a document. | Source handoff requires deliberate authorization from the current owner, validation of representable semantics, and fencing/revocation of the previous writer. No general reverse compiler for arbitrary Rust is promised. |
| **Conditional change** | Semantic and layout writers independently check an expected predecessor revision **and** the authoritative owner/source generation (or an equivalent conflict-proof precondition). A stale or competing edit fails visibly with no accepted state overwritten. | Exact optimistic-concurrency token, authoritative storage location, transactions, conflict resolution and persistence mechanism are separate design decisions. Concurrent layouts do not implicitly write semantic plans. |
| **Candidate vs activation** | Saving or validating a proposed new semantic revision does not automatically activate it, replace an in-flight run, or grant remote control. Existing runs remain bound to their immutable revision. | Who may publish/activate, how application identity/artifact authorization is verified, and crash/uncertain-outcome reconciliation require separate #111/#75/#60 decisions. |

**Version/identity safety across layouts, sources and sessions:**

1. An accepted semantic revision's meaning cannot change in place. Invalid plans, stale authoring owners, mismatched binding catalogs or stale predecessors reject before mutation; no direct update of an already admitted run. A layout-only save never allocates an executable semantic revision or changes callback admission.
2. Layouts may be associated with historical semantic versions; opening one is not approval to execute an old plan. When a plan gains/removes nodes, a new layout may be derived only through explicit checked rebase with diagnostics. The original layout and its historical anchor remain distinguishable. Layout storage and semantics storage need not share an atomic transaction, but no mixed-version view may masquerade as a current authoritative plan.
3. A Rust-to-document transfer requires a verified current source owner and an explicit compatibility report for every executable construct; unsupported or unknown Rust behavior must block executable migration or stay read-only. The new source must not become authoritative simultaneously with the old source. Restoration or document-to-code transfer is likewise a deliberate accepted-source operation, not an automatic generated-code round-trip.
4. A conditional-write mechanism must reject stale writers after semantic commits, after layout commits in that presentation stream, after owner/source transfer, or after publisher/artifact replacement. An off-line editor or malicious client cannot acquire authority by copying a plan ID, guessed revision number, app name or token intended only for correlation. Exact compare-and-swap / hash / fencing representation remains an implementation question.
5. Faults between authoring, validation, publication, durable storage and activation must retain enough authoritative state to distinguish **not applied**, **applied**, and **outcome unknown**, rather than automatically retrying a possibly dispatched activation or treating missing acknowledgement as rollback. The application/runtime's current session/attempt and domain-authority guarantees continue to apply. No automatic hot swap, multi-writer distributed consensus or exactly-once effects are implied.
6. **Preserve S2→S3 evolution:** S2-only plans keep control-dependency meaning under S3-aware semantics. New typed-value edges would be a new **semantic revision** with separately declared required features and ports; an S2-only executor fails closed, and an old editor cannot discard unknown executable fields. Layout changes never promote a control edge to an executable value transfer, and revising data contracts does not retroactively change historical runs.

**Minimum verification before a production V2 facility may be claimed:** independent semantic/layout revision collision tests, stale-writer and source-epoch fencing, conflicting editor saves, checked layout rebase across node removal/rename, failed/partial source transfer, unknown S3 feature preservation or rejection, unchanged in-flight run identity, a simulated crash between save and activation with explicit reconciliation, and authorization/provenance denial on an untrusted publisher. The [#169 test-only separate layout sidecar](https://github.com/aschenrot/riesel/pull/169) verifies only a bounded in-process subset; it is **not** evidence that these durability/concurrency/authorization tests already pass.

### First editable subset — accepted S2, S3 evolution preserved (#111)

**Owner decision:** [S2 accepted conditionally on a credible, future-proof S3 path (22 November 2026)](https://github.com/aschenrot/riesel/issues/111#issuecomment-7074822182). The *first* supported editable executable plan is **bounded registered control-flow composition** over the shared Riesel execution semantics, with the code/document one-authority-per-plan choice already accepted above. **Later executable typed dataflow (S3) remains a feasible, explicitly versioned product evolution target**, not a guarantee of a cost-free migration or approval of a typed runtime now.

**Allowed semantic changes (once an implementation is independently accepted):** a document-owned editor may add/remove named nodes, select exactly versioned **application-publisher-authorized registered operations**, add/remove **control-dependency** links, and edit only expressly permitted signal triggers and symbolic resource/domain-admission declarations. Every proposed edit must be validated as a whole and exact-bound without invoking handlers or starting providers; invalid, unsupported, or stale changes must fail without partially affecting an executable plan. Edits result in new immutable semantic revisions and cannot mutate an active run. Code-owned plans remain read-only in the editor unless a separately defined source-of-truth handoff explicitly preserves or rejects unsupported Rust semantics.

**Editor-safe descriptors are distinct from runtime bindings:** the application/publisher controls which registered operation identities and versions are selectable and which declarative fields may be changed. The existing `OperationRegistry<H>` contains trusted Rust handler objects but does **not** itself advertise a safe-to-edit schema, source authority, executable data ports, or authorization to external clients. **Safety-critical declarations must be trusted and binding-authoritative:** registered operation/domain ownership must supply or attest compulsory resource-access, affinity and admission constraints, and preflight must reject an edited plan that omits, weakens or contradicts them. Publisher-exposed alternatives may be selected only if they retain the required invariants; a graphical editor's resource or domain fields are never the sole truth about an opaque Rust callback. Current SDK resource declarations by themselves do **not** prove Rust alias safety. Valid metadata is not a permission to publish or execute. Domain admission ownership and `!Send`/native-affine resources cannot be transferred or reclassified by an editor.

**Mandatory S2-to-S3 evolution and compatibility constraints:**

1. **Preserve control semantics.** S2 dependency edges express prerequisite admission only: they must never be silently upgraded to data-value edges. S3, when specified, will require distinct typed inputs/outputs/value edges, data-ready and failure semantics. S2 plans without those new semantic features must retain the same validated meaning and supported execution behavior in an S3-aware engine. A separate interpreter or parallel graph scheduler must not be introduced simply because a plan is visually authored.
2. **Explicit semantic version/feature negotiation.** Future executable data edges and binding/port descriptors need independently specified, discoverable version and required-feature semantics. An S2-only executor must reject unsupported S3 execution **before dispatch**, never ignore an unrecognized executable field. A read-only inspector may indicate unsupported features and preserve source bytes for a future compatible editor, but an older writer must not silently strip unknown semantics on save. This constraint does **not** select a concrete document/JSON schema or demand placeholder ports in S2.
3. **Stable identities and explicit migrations.** Preserve logical plan/node IDs and exact registered operation key/version meaning; do not mutate an existing accepted revision. Any new typed handler signature, port type, default or transport contract must have a deliberate compatibility adapter or explicitly new version. Adding value edges creates a new semantic revision; view/layout-only changes must not. Source-of-truth transitions, schema migrations, publisher/artifact provenance and concurrent editor conflict handling remain separately specified.
4. **Typed execution safety.** Before S3 can be advertised, specify and verify value lifetime/ownership, Rust borrow and `!Send` affinity, serialization and trust boundaries (where applicable), type compatibility and error/unknown outcomes, **combined control-and-data cycle detection**, admission/data-ready coordination and resource conflict rules. A string-labeled port type equality check alone cannot prove safe executable transfer. Delegated ECS/system schedules retain their owner; Riesel does not automatically move a world, GPU resource or thread-confined object across processes.
5. **Scalable bounded execution.** Preserve the current session-owned runner's admission/ownership and snapshot/control contracts for S2-only graphs. Any future payload transfer must specify and test finite value/queue/memory budgets, backpressure, fan-out and copy behavior, cancellation cleanup, high-volume value paths, and no mandatory data buffering on graphs that have no executable data edges. No numeric latency/throughput or zero-copy guarantee has been demonstrated. Compare domain-local/owned handoff and serialized/streaming materialization in realistic workload-specific research before accepting S3 mechanisms.

**Required future S3 acceptance evidence:** regression tests keep old S2 code/document graphs executable unchanged in an S3-capable engine; unknown S3-required semantics fail on an S2-only engine; incompatible ports/operation versions reject before execution; no lossy unknown-field editor round-trip; existing run identities, domain authority and revision fences remain intact; negative `!Send`/cross-process cases prove the declared ownership boundary; measured CPU, memory and transfer latency cover representative async services and simulation/data-intensive graphs. These are **future tests**, not claims currently met by #83 or the [research-only production-plan tests in PR #169](https://github.com/aschenrot/riesel/pull/169).

**Migration cost and limits:** existing IDs, dependency semantics, executor ownership and observer identity can remain conceptual foundations, reducing *semantic replacement* pressure. Actual S3 adoption still requires document/descriptor evolution, typed-edge validation, operation adapter signatures, storage/codec/lifetime policies, data-ready admission, resource budgets and compatibility tests; individual app bindings may need explicit revision upgrades. No automatic migration of arbitrary Rust source, free typed transfer, general dataflow execution, universal ECS debugger or fixed API is accepted.

**Still open in specification #111:** the **mechanisms** (not the already accepted V2 principles) for durable semantic/layout ID and revision allocation, canonical document/schema and compatibility migration, explicit source handoff/report/fencing, the concrete versioned editor-safe descriptor catalog and permission policy, artifact provenance and passive inspection without executing untrusted code, conditional writes/conflict resolution, authorized publication versus safe activation/reconciliation, and cross-process authorization coordinated with #75/#60. These remain **specification gates**, not public editor implementation approval. Arbitrary Rust closure serialization, arbitrary resource transfer, automatically generated ECS system schedules, undocumented hot replacement and unrestricted visual programming are not accepted guarantees. A read-only visual graph does not itself satisfy the edit/execute outcome.

## Implementation and acceptance sequencing

Implementation issues must be separately testable and grounded in this accepted direction; they may proceed in parallel only where an agreed interface makes them independent.

1. **Plan and binding foundation:** inspectable immutable plan identity/revision, strict validation and explicit executable registration; headless operation without starting providers during static validation. Verify invalid/cyclic/unknown bindings fail closed and a running revision remains unchanged after edits.
2. **Reusable run coordinator:** bounded generic graph eligibility and execution for supported Rust/typed-capability operations, with explicit delegated domain boundaries, cancellation/error propagation, existing session/task ownership and concurrency/access constraints. Verify both event-driven async branching and fixed-tick workloads against the same advertised semantics.
3. **Authoritative state, effects and cooperative control:** run/session/attempt correlation, snapshot and observable transitions, partial/unknown outcomes, bounded trace loss and resync, generation-fenced owner-specific safe points. Verify stale control rejection, unknown results, committed-prefix preservation and live control without impeding unrelated work.
4. **Optional nested owner projection (#146):** independently of a graphical frontend, allow a participating domain owner to publish a correlated read-only nested view while keeping the existing outer-only fallback. Verify the owner/generation and bounded-loss semantics across real Bevy ECS, RunenECS and a non-ECS pipeline. Do not introduce domain-internal controls or external publication as part of this slice.
5. **Optional inspector:** a toolkit-neutral observation projection or consumer that demonstrates a graph/timeline without independent authority. An actual independent graphical frontend requires its own supported interface and authorization gate; it is not required before headless gates.
6. **Visual editor specification (#111):** apply accepted option C, first-subset S2 with S3 evolution protections, and V2 separate immutable semantic/layout revisions with explicit source transfer and stale-write rejection; finish descriptor/catalog mechanism, document compatibility, persistent identity/fencing, artifact/publisher authorization and safe activation before opening executable editor implementation work.

Research [#83](https://github.com/aschenrot/riesel/issues/83) supports these decisions but **does not** prove public compatibility, production authorization, durable replay, arbitrary `!Send` scheduling or faithful visual authoring. This plan is **accepted product/architecture direction**, not a statement that any gate has been implemented or that the platform is production-ready.
