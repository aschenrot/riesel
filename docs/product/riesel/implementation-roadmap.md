## Stage 5.7 — verified lifecycle delivery

Optional `ApplicationModule` registrations now include named, typed async start/stop hooks using the existing `Application` builder, capability DAG, `RunningApp` session and `AsyncTasks` owner. The runtime creates no additional scheduler or provider resolver. Invalid registrations fail before startup; normal shutdown drains owned work before eligible stop hooks and provider teardown. Capability-dependent cleanup is skipped after session revocation.

Counter integration tests verify order, partial startup cleanup, combined error sources, local/managed parity and fresh hooks after a real managed crash. Stage 5.7 acceptance evidence: [Issue #10](https://github.com/aschenrot/riesel/issues/10), [implementation PR #14](https://github.com/aschenrot/riesel/pull/14), and [Linux validation and smoke](https://github.com/aschenrot/riesel/actions/runs/44530550169). Precise semantics and limitations: [application modules](application-modules.md) and [runtime lifecycle](runtime-lifecycle.md).

## Stage 6 — Production reliability (not a release promise)

The first bounded Storage slice is delivered through linked SQLite and opt-in SDK registration. The [Todo product](../todo/todo.md) now exercises it through persistent R1 headless commands and a local-only R2 SvelteKit/browser integration with a Riesel-owned HTTP session. The in-memory R0 regression example remains separate. These **product-level acceptance scenarios** do not establish complete Stage 6 reliability or general production release readiness.

The [Stage 6 offline SQLite model migration contract](sqlite-offline-migration-architecture.md) was **accepted on 2026-11-20** after [specification #41](https://github.com/aschenrot/riesel/issues/41). Cooperative owner exclusion ([#48](https://github.com/aschenrot/riesel/issues/48)) and bounded offline verified backup/restore ([#49](https://github.com/aschenrot/riesel/issues/49)) have met their **first supported single-host Linux** acceptance gates. An explicit, bounded typed transactional migration execution API is now implemented ([#50](https://github.com/aschenrot/riesel/issues/50), [PR #70](https://github.com/aschenrot/riesel/pull/70)), including a verified recovery snapshot, full source/target schema checks, revision fencing and transaction rollback. Registered application-level cross-model invariants are evaluated against the proposed target state before commit ([PR #72](https://github.com/aschenrot/riesel/pull/72); [exact merged-main Linux validation](https://github.com/aschenrot/riesel/actions/runs/44786506821)). The bounded typed transactional engine has passed its accepted cooperative offline Linux gate ([#50](https://github.com/aschenrot/riesel/issues/50), [merged-main CI 44793344901](https://github.com/aschenrot/riesel/actions/runs/44793344901)). The deliberate operator preview/execute/restore workflow ([#51](https://github.com/aschenrot/riesel/issues/51)) delivers the **first bounded cooperative Linux operator acceptance scope**. A separate Rust application supplies derived historical/current models and deliberate transforms; the CLI reports finite capacity envelopes, requires exact independently confirmed artifact paths, retains verified snapshots and refuses approval-time source drift. Recovery, partial-backup behavior, unavailable legacy-process exclusion and post-commit uncertainty are documented in the [operator runbook](sqlite-offline-operator-runbook.md). Broader reliability and release hardening remain separate. No startup-triggered migration, online evolution or uncooperative legacy-binary isolation is supported.

Plan and separately accept production features by user value and operational risk. Current candidates:

| Area | Required future outcomes |
| --- | --- |
| Storage | Linked durable backend, cooperative ownership and bounded offline snapshot/restore delivered; typed engine and explicitly approved operator preview/execute/restore delivered for bounded cooperative Linux scope; broader schema/versioning, operations and release hardening separate |
| Networking | Authenticated/authorized remote transport, trust establishment and secrets handling |
| Runtime | Operational metrics, configurable resource budgets and safe stateful recovery contracts |
| Tools | Manager/discovery workflows, platform CLI parity, and repeatable deployment |
| Interfaces | Reusable P3/T1 optional local non-sensitive read-only application attachment is accepted, but not yet delivered; independently operated browser/native/specialized GUI hosts remain frontend choices |

Selective provider restarts with transparent rebinding, distributed orchestration, automatic multiplayer, UI frameworks and **unrestricted visual application building** remain **exploratory** until independently scoped and justified. The accepted bounded execution-plan/visual-inspection direction is tracked separately below. Current loopback plaintext RPC and in-memory reference Storage are not production equivalents.

## Accepted typed Query and linked Record Query — initial linked profile delivered

The owner accepted **optional typed Query semantics with provider/domain-owned execution** and, for first registered-record delivery, **a separately versioned read-designated Query facet** co-exposed with Storage v2 by **one verified linked model/data owner**. Query performs bounded retrieval; Storage or domain-specific capabilities retain mutations. Typed read-only consumers must not require write capability. A combined reader/writer must use one declared data authority and fail preflight/runtime if linked binding splits or lacks the requested consistency. Keep Storage v2 compatibility and do not impose an engine on ECS/spatial/search/streaming domains.

[Accepted architecture](record-query-architecture.md) and [specification #138](https://github.com/aschenrot/riesel/issues/138#issuecomment-7073879626) have their **first trusted-linked record implementation delivered**: [#160](https://github.com/aschenrot/riesel/issues/160) implemented typed model registration and fail-closed same-owner/session binding; [#161](https://github.com/aschenrot/riesel/issues/161) delivered separate `riesel.query.records@1` read-only native Memory/SQLite providers, bounded typed predicates, model grants, finite live cursors and typed Query-only/combined read-write consumers via merged [PR #177](https://github.com/aschenrot/riesel/pull/177). The exact protected integration candidate passed [Linux Validate and smoke #44993803283](https://github.com/aschenrot/riesel/actions/runs/44993803283) and [Nested Observation Acceptance #44993803316](https://github.com/aschenrot/riesel/actions/runs/44993803316) at `2f28ac0` before merging into `main` at `3f45fea`. [Typed usage and limitations](record-query-usage.md) remain specific to **trusted linked registered records**. Independent client/GUI publication, remote grants, generalized ECS/game/spatial Query, physical indexes and stronger snapshot/distributed consistency require separate scope and #75/#60 security acceptance; they are **not** delivered by this milestone.

## Shared operational architecture — internal runtime delivered, P3/T1 GUI publication accepted

The [owner-accepted #75 decision](https://github.com/aschenrot/riesel/issues/75#issuecomment-7073783350) establishes **shared transport-neutral operational semantics with independent product adapters**, documented in the [durable operational contract](operational-contract.md). Application/registration/artifact/OS-attempt/session/interface/client identities, evidence-scoped readiness, deliberate export, scoped permission, revocation and uncertain mutation outcomes have common meanings; no daemon, protocol, production exporter or security implementation is thereby delivered. The [delivery model](../../project/delivery.md) governs separately verifiable implementation Issues and exact-revision CI.

**Verified partial implementation (22 November 2026):** the test-only internal **#157 runtime session generation, bounded ingress and owned async recovery** foundation is merged in [PR #162](https://github.com/aschenrot/riesel/pull/162), [PR #170](https://github.com/aschenrot/riesel/pull/170) and [PR #173](https://github.com/aschenrot/riesel/pull/173). The final real managed Counter async recovery fixture passed [dedicated ingress CI #44989495744](https://github.com/aschenrot/riesel/actions/runs/44989495744) and [Linux Validate/smoke #44989495720](https://github.com/aschenrot/riesel/actions/runs/44989495720) before protected integration at `ed92cb6e861189bc8657b09ad568bd56e985974c`. It proves same-PID generation fencing, old request cancellation/join, bounded admission and test-adapter withdrawal **without** a public exporter, verified client principal or OS authority. [#157](https://github.com/aschenrot/riesel/issues/157) remains under its own final cross-workstream acceptance audit.

**Verified narrow outcome slice:** [Todo HTTP PR #171](https://github.com/aschenrot/riesel/pull/171) distinguishes rejected-before-dispatch from a reply lost after a real stored mutation (HTTP `outcome_unknown`), without automatic replay. General source-/freshness-qualified lifecycle/readiness observations across Counter, Todo and developer workflows are **not delivered** and remain [#158](https://github.com/aschenrot/riesel/issues/158).

**GUI publication architecture accepted (22 November 2026):** [#248 P3 + T1 owner decision](https://github.com/aschenrot/riesel/issues/248#issuecomment-7084595587) selects an **optional application-owned boundary** exposing only deliberately selected versioned app-facing capabilities through reusable session, admission, withdrawal and loss-aware read semantics, with independently chosen frontend/rendering and transport adapters. First supported external GUI access is **local, non-sensitive and read-only**, under an explicit shared-OS-user trust assumption. It does not exclude malicious same-user processes or provide verified individual client/server identity. Sensitive observations, writes, graph commands, executable plan publication/activation and Manager operations retain separately protected authorization gates. No public exporter, general client authentication or supported live GUI connection has been implemented as a result of the architecture decision. Exact research evidence: [three-app comparison #252](https://github.com/aschenrot/riesel/pull/252), [live graph viewer #250](https://github.com/aschenrot/riesel/pull/250), [real process/recovery/loss and counterfeit endpoint #256](https://github.com/aschenrot/riesel/pull/256). Their independent successes are not one integrated protected product.

**Delivery boundaries:** implement and verify the shared P3/T1 opt-in publication/attachment foundation under [implementation #258](https://github.com/aschenrot/riesel/issues/258) and the accepted [operational contract](operational-contract.md), then deliver the independent graphical inspector under [#114](https://github.com/aschenrot/riesel/issues/114). Retain native-window #60 research and existing Todo HTTP as inputs; do not force migration or a selected renderer. Progress [#68](https://github.com/aschenrot/riesel/issues/68) and graph/nested-domain work independently. Privileged OS process control, protected CLI/browser and installed lifecycle remain [#59](https://github.com/aschenrot/riesel/issues/59); no local UID/label proof may be presented as hostile-same-UID Manager authorization. Windows/macOS production and applicable manual OS evidence remain separate gates.

## Accepted execution-plan and inspector outcomes — headless reference delivery

The [execution-plan contract](execution-plan-contract.md) accepts **headless executable operation composition**, a reusable general graph runner with explicit nested-domain ownership, authoritative run inspection and cooperative safe-point control. **Optional visual inspection** is accepted as a product goal. Editable executable visual graphs remain a **long-term direction**. [#111 owner-accepted option C](https://github.com/aschenrot/riesel/issues/111#issuecomment-7074722751) establishes **shared validated semantics and one explicit authoritative authoring source per plan**, preserving Rust-first authoring while supporting future document-owned visual plans; [S2](https://github.com/aschenrot/riesel/issues/111#issuecomment-7074822182) is now the owner-accepted **first bounded registered control-flow edit subset**, conditional on preserving a versioned, compatible path to later **S3 executable typed dataflow**. [V2](https://github.com/aschenrot/riesel/issues/111#issuecomment-7075163935) additionally accepts **separate immutable executable semantic and non-executing layout revisions, explicit Rust/document source-authority handoff, and stale-writer fencing**. [A2+B2+C3](https://github.com/aschenrot/riesel/issues/111#issuecomment-7075539465) completes the accepted **first-editor architecture**: application-owned versioned editor-safe descriptors, strictly validated and explicitly feature-versioned executable documents with safe read-only future-unknown handling, and application-authoritative immutable publication with separate authorized runtime activation. **Implementation progress (trusted-local profile):** the opt-in app-owned editor-safe operation catalog and exact binder are merged ([#191](https://github.com/aschenrot/riesel/issues/191), [PR #197](https://github.com/aschenrot/riesel/pull/197)); #191 remains open for its full evidence/provenance acceptance. The tested upgrade uses separately compiled application executables; the build-correlation label is **not authenticated installed-artifact provenance**. Application-authoritative plan publication and separately authorized activation ([#195](https://github.com/aschenrot/riesel/issues/195)) remain open; no executable graphical editor, external publisher grant or active-plan hot replacement is delivered. Future S3 typed-value execution remains separately specified in [#187](https://github.com/aschenrot/riesel/issues/187). **Delivered and tested within the reference scope:** immutable validated plan/binding and static read-only inspection ([#110](https://github.com/aschenrot/riesel/issues/110)); a bounded session-owned one-shot graph runner with async/event-driven branches, session-wide resource/domain admission, managed-process crash and task-drain regressions, explicit external-clock fixed-step proposals and repeatable independent runs ([#112](https://github.com/aschenrot/riesel/issues/112)); authoritative read-only in-process run identity/snapshots/loss-aware transitions, bounded owner-confirmed effect prefixes and local cooperative run/operation/Riesel-owned outer-domain-tick admission controls ([#113](https://github.com/aschenrot/riesel/issues/113)). ## Accepted node-workbench outcome and optional S3 architecture — separate delivery gates

**Direction accepted on 22 November 2026:** [#175 bounded node-based Grid Workbench](https://github.com/aschenrot/riesel/issues/175#issuecomment-7076113507) and [#187 optional typed-value execution with explicit domain ownership](https://github.com/aschenrot/riesel/issues/187#issuecomment-7076117427). Both specification issues **remain open** for decision-critical remaining interfaces and verified integration; these are **not delivered**, nor does acceptance authorize merging their isolated research PRs. This direction builds on, and does not replace, the completed #111 C+S2+V2+A2+B2+C3 architecture and existing S2 implementation issues.

| Delivery boundary | Prerequisite / exit evidence | Current state |
| --- | --- | --- |
| Neutral upstream Grid algorithms | Review scalar noise sampling/precision/seed/space separately from threshold; configurable synchronous CA protected-write and OOB-read semantics; preserve authoritative dual-grid mask/topology/dirty corners, all 16 cases, and exact-version domain CI | Grid #2 production contract acceptance remains open; its test-local scalar/CA proof passed hosted Linux CI on recorded research revisions |

| Reusable S3 executable typed ports | Finalize app-attested exact handler type/port binding, data-ready/failure/unknown admission, version/feature gates, ownership/affinity, fan-out/retention/backpressure and unchanged low-cost S2; one existing graph runner | Architectural direction accepted, specification #187 still open, no public S3 implementation |
| Editable graph experience | Rust/document authoring uses one authoritative plan source, immutable semantic/layout revisions, typed connector validation, selective recomputation and inspectable errors; first S2 editor and #60/#75 external grants are independent prerequisites when relevant | Product goal accepted, node editor not implemented; a read-only projection or S2 control-only composer is insufficient |
| GUI-neutral visual editor/inspection (optional to headless operation) | Define the application's versioned graph/result view and authorized commands; deliver one working visual editor adapter, with Bevy-based, custom-native and web hosts remaining eligible; preserve independent native-host lifecycle and explicit client grants | Editor-facing contract/host adapters not implemented; #60/#75 remain separate security and lifecycle gates |

**Order:** settle upstream Grid neutral operation contracts and #187 required semantic gates in parallel; validate real headless Grid app using supported outer runner and domain-owned typed artifacts; implement backend-authoritative typed graph edit/execute semantics once the relevant contracts are accepted; deliver the visual node editor through at least one verified GUI adapter, without making its toolkit a platform dependency or a prerequisite for headless execution. Create production implementation issues only once the respective behavior/ownership/compatibility boundaries are concrete and owner-accepted. Do not gate existing S2 implementation on speculative S3 delivery, and do not require a Manager or renderer to run a headless Grid Workbench.

## Validation, risk and release rules

```sh
cargo validate --check
cargo smoke
```

Linux CI is the development quality gate for changes that affect executable behavior. A passing check is tied to **one exact commit**, not an indefinitely green branch. The release procedure must additionally run Windows manually and evaluate production-specific security, durability and operational claims; it cannot infer them from these reference tests.

Key current limits: cooperative Rust work can block shutdown; dropping an async RPC future does not undo already transmitted commands; a whole-session restart may replay entrypoint work; in-memory provider state is lost on restart; the provider handshake validates declared metadata rather than authenticating a peer. See [runtime lifecycle](runtime-lifecycle.md) and [async execution](async-execution-contract.md).

## Work management

The roadmap records outcomes and stages, not individual commit history or a second task list. Actionable work, acceptance evidence and exceptions belong in GitHub Issues/PRs under the [delivery model](../../project/delivery.md). Implementations need one coherent reviewed change and relevant tests, not one commit per checklist item.
