# Riesel — Accepted linked Record Query architecture

**Status:** Accepted technical direction, **not implemented** (22 November 2026).  
**Decision:** [Specification #138 — owner acceptance](https://github.com/aschenrot/riesel/issues/138#issuecomment-7073879626).  
**Research:** [same-task conformance evidence](https://github.com/aschenrot/riesel/blob/research/general-query-138/research/query-architecture/INTERFACE_CONFORMANCE.md), [decision review](https://github.com/aschenrot/riesel/blob/research/general-query-138/research/query-architecture/DECISION_REVIEW.md); [research PR #140](https://github.com/aschenrot/riesel/pull/140) is not implementation.  
**Scope:** first trusted *linked*, same-application-session registered-record query profile, with an extensible boundary for independently accepted future placements and specialized domains.

## Product outcome and chosen boundary

Riesel supports an **optional, reusable, transport-neutral typed Query semantic foundation** for capability-owned data, with physical evaluation and authorization remaining with the authoritative provider or domain. The **first registered-record realization** uses a **separately versioned, read-designated capability facet**. It is distinct from the existing mutating Storage v2 capability but can be co-exposed by **one linked data-owner component**.

**Query reads; Storage and domain-specific mutation capabilities write.** Create, update, delete, transactional mutation and authoritative application state changes are not methods of the read-designated Query facet. Applications needing both compose capabilities; Query-only applications do not implicitly request the writable Storage RPC contract.

This is an architectural choice for a supported record domain, **not** a compulsory universal executor, SQL language or Query API for game/ECS, spatial, graph, search, streaming and analytical providers. A domain may share semantic vocabulary where valid while retaining its own evaluation, validity scope, scheduling, lifecycle and mutation rules.

## Supported first profile: authority and consistency

1. **Declared per-dataset authority.** An application explicitly identifies the logical registered-record model/dataset authority and the read and optional mutation roles it requests. Models can be registered independently of mutation authority. Unrelated model datasets may use different owners. A developer should not have to manually synchronize two independent provider aliases for one intended read/write dataset.
2. **Linked read/write affinity.** For immediate read-your-writes, Query and Storage v2 facets must select one **compatible linked component registration** and actually attach to **the same instantiated owner** inside the current Riesel application session. A confirmed, sequential write must be visible to a subsequent supported live Query read. Preflight rejects missing, ambiguous, separately selected or incompatible providers and unsupported consistency **before constructing local provider state or starting side effects**; attachment/runtime checks verify the actual instance/session rather than relying on planned equality alone.
3. **Read-only model applications.** SDK typed parameters and explicit builders support Rust-derived model declaration and read-only Query registration *without* adding a writable Storage requirement. The generated canonical application schema must expose model identity and the read authority relationship; it must validate equivalently from macro and builder authoring. Storage v2 clients need no migration to use their existing capabilities.
4. **No implicit cross-application reader.** A separate process or app is **not** automatically authorized to read an existing linked owner's data merely because its model, provider type, SQLite path, endpoint, UID or capability contract matches. The initial linked profile requires no exported remote endpoint. Future independent clients, proxies and replicas need a separately accepted publication, security, authority and consistency profile.
5. **Provenance and lifecycle.** Linked provider selection is established before initialization; runtime checks use the actual created instance and current session. Session recovery invalidates stale handles/cursors. Identity claims derived only from aliases, lifecycle depends_on ordering, provider-definition metadata, selected managed instance names or physical database paths are insufficient. A stale or unsupported binding fails closed, not with silent fallback to a second dataset.
6. **No automatic universal relation layer.** Implement the smallest coherent **model/dataset-scoped binding relationship** that satisfies these invariants. Do not introduce a generic capability authority-group or cross-domain ownership registry without independent requirements and evidence. A future remote relation may refer to one logical source through a trusted proxy or explicitly stale replica without requiring physical co-location.

The first **read-your-writes** guarantee is deliberately narrow: a confirmed completed write followed by a supported read on the same attached linked owner in one app session. It does **not** promise an atomic multi-record transaction, a stable multi-page snapshot, exactly-once writes, cross-process synchronization, automatic rebind across restarts or immediate reads from a replica. Unknown write outcomes remain unknown and must not be silently retried or upgraded to success.

## Typed Query semantics and resource correctness

The first record Query implementation must define and test an **explicit supported profile**, not infer correctness from whatever a backend SQL engine happens to accept.

- **Models and values:** identify registered model/schema and supported field types. Preserve full-width Rust numeric identity (including u64), UUID normalization, missing-versus-present-null and optional-field semantics. Reject invalid operands or unsupported operators rather than coercing into a different truth value.
- **Selection:** advertise supported typed predicates, ordering, bounds and continuation. Define tie-breaking and deterministic order when claimed. A sorted live cursor does not imply a snapshot: if data changes between pages, duplicate/missing results can occur unless an explicit stronger consistency guarantee is delivered.
- **Bounded work:** bound **execution effort**, result size and transport size; merely limiting returned rows is insufficient for sparse selection. Providers may reject a request or interrupt evaluation when cost limits are exceeded. Return distinguishable exhausted/partial/unsupported/budget/invalid-cursor or invalid-session outcomes; an incomplete page must not masquerade as an empty complete result.
- **Continuation validity:** bind opaque continuations to the relevant model/schema, supported query profile and predicate/order, authority, session generation and consistency level as needed. A stale or mismatched continuation fails explicitly; no automatic restart or silent traversal of another dataset.
- **Execution ownership:** linked Memory and SQLite execute their own supported operations and index choices while conforming to the **same observable typed profile**. Physical planner and index technology are provider details, not part of a shared mandatory Riesel engine. Unsupported capabilities are surfaced and not emulated by a silently unbounded full scan.
- **Visibility and diagnostics:** an inspected application/provider plan must reveal which model and read/write roles are declared and what compatible capability/consistency profile is selected, without claiming to authenticate an external peer.

The precise published operator vocabulary, AST, transport encoding, cursor format, numeric limits and name/version of the public read contract are **implementation design matters subject to the acceptance tests below**. This decision accepts their required semantics, not a speculative serialized API.

## Least privilege and trust boundaries

A **read-designated operation surface** must genuinely exclude mutation commands from the published Query facet. A Rust-only wrapper around a writable Storage contract does not meet this requirement; its underlying RPC still contains create/update/delete. Provider-local model visibility and access rules must be enforced at the data boundary, not solely in presentation or SDK convenience types.

The **first trusted linked** profile is not a hostile same-user isolation or untrusted process security claim. Contract shape by itself does not authenticate external callers, issue grants or provide revocation. Any later app-facing or managed/external reader must use the accepted shared operational identities and security semantics from [#75](operational-contract.md), independently accepted [#60](https://github.com/aschenrot/riesel/issues/60) publication, actual issuer/client-principal verification, model/operation permissions and session-generation fencing. Loopback TCP, a provider identity pin or a matching UID does not constitute authorization. Deny unsupported remote access instead of weakening the guarantee.

## Compatibility, state and evolution

- Keep the public **Storage v2 contract and existing Rust model authoring** compatible for current applications. Version the new Query facet and its profile separately. Do not silently make existing Storage providers or every Riesel capability implement Query.
- Current application-schema v1 rejects unknown fields and has Storage-oriented model_bindings and independent requirement selections. This decision **requires an explicit compatible schema/resolver/SDK evolution** for read-only model declarations and linked role/authority relationships; it does **not** choose a field name, serialized representation or claim compatibility is automatic.
- Validate compatibility of generated macros, typed handlers, explicit builders, schema roundtrips, provider catalog inspection and side-effect-free deployment plans. Fail clearly for unsupported schema/profile versions; prevent false success from legacy aliases, depends_on or matching provider-definition metadata.
- Keep persistent SQLite **physical indexes, expression-index maintenance, database format changes and their backups** outside this first logical capability-contract acceptance. They require separate opt-in, offline owner exclusion, migration/recovery, rollback and performance/correctness validation consistent with [accepted offline migration boundaries](sqlite-offline-migration-architecture.md); do not execute silent startup DDL.
- Preserve explicit future evolution paths for authorized independently published Query, replicas with declared freshness, better consistency profiles, advanced provider-native indexes and specialized domain adapters. These are **not** shipping commitments or bypasses of the relevant security and ownership gates.

## Implementation sequencing and acceptance gates

Implementation belongs in **separately tracked, independently verifiable Issues** after this decision and its authoritative documentation are integrated:

1. **Typed model-only declarations, schema and fail-closed owner selection.** One canonical inspectable representation for model/read roles and optional writer pairing, with SDK/macro/builder parity, backwards-compatibility checks and side-effect-free preflight rejection of split/missing/ambiguous linked providers. Actual same-owner/session binding and invalidation must be tested, not merely assumed from matching names.
2. **Versioned read facet and native linked providers.** Deliver narrow, provider-owned Memory and SQLite read capability implementations with a precise, agreed subset of typed operators and bounded work. Verify read-only capability surface, provider-side model constraints, exact numbers/UUID/null, opaque continuation and budget/unsupported errors, live read-your-writes, and existing Storage v2 file/API compatibility.
3. **Consumer integration and regression.** Demonstrate a typed Query-only app and a combined record read/write application, including Todo where its separate accepted UX outcome benefits from Query. Show generated inspectable definitions, no accidental write permission, selected provider affinity, stable existing CRUD and honest partial/empty UI. No broad cross-domain executor or remote grant is necessary for this acceptance.

The work may be reorganized into coherent implementation PRs if source-level dependencies warrant it, but **not** weakened to a Todo-only in-memory filter or a read-wrapper over writable Storage. Runtime mutations, actual provider behavior and exact-commit Linux validation are mandatory for implementation acceptance. Windows remains a manual pre-release check; research CI alone does not satisfy delivery.

## Alternatives, falsifiers and decision ownership

[Research #140](https://github.com/aschenrot/riesel/pull/140) compared a separate read facet, an evolved/unified attenuated Storage contract, model-authority facet composition, domain-owned reads and other approaches against the **same** typed-only reader, read/write affinity, independent client, typed correctness and evolution tasks. A test-only unified Storage adapter **really refused a write inside the provider**; this demonstrates viable server-side policy, but the mutating Storage contract still advertised write commands and did not prove client-specific grants. A composite SDK handle alone likewise did not prove common data authority.

The **owner accepted separate read packaging for the initial linked record profile** because it enables independently versioned Query and a genuinely narrower read contract while retaining Storage v2. If implementation experiments reveal that a verified authority relation cannot meet the required safety/ergonomics without a material regression, **reopen #138's decision through the delivery exception workflow** rather than silently substituting a unified writable interface or accepting split state. A different later workload is not retroactive evidence of a defect in this bounded first profile.
