The candidate shared-model approach is **preferred for review** over (A) independently duplicated product conventions and (C) mandatory control daemon. It reuses the runtime as session authority while allowing replaceable process/toolkit/transport adapters. This choice is **not yet a frozen SDK or protocol**. A mandatory service adds an operational single point of failure without established user benefit; independent adapters risk conflicting session and error meanings. Neither “minimal patch” nor “maximal framework” is an architectural argument on its own.

## 2. Proposed common semantics for #75

### 2.1 Identity and authority must not collapse

| Concept | Authority | Stability / non-equivalence |
| --- | --- | --- |
| Application definition and published logical identity | Application author / SDK contract | Stable within deliberate version policy; not a running process or security proof |
| Executable build and deployment provenance | Cargo/build tool, trusted installation or supervising operator | Artifact/config identity; a filename or application display name is insufficient |
| Manager registration | Manager's trusted registry | Stable across launches; not a runtime session or proof that an arbitrary binary is trustworthy |
| Launch attempt / OS process-owner reference | Owning foreground tool, Manager policy or OS service | One owned process attempt; PID and reused service name alone are insufficient |
| Riesel application-session generation | **Riesel runtime**, on each whole-session start or recovery | Fresh and non-reusable for that runtime session; distinct from PID, provider generation, gateway/transport lifetime; **not a bearer credential** |
| Provider instance | Runtime and selected provider owner | Distinct from entire application and published interface |
| Published application interface + contract version | App/session, using explicit author selection | Explicitly allowed operations, independently versioned; no implicit internal-provider exposure |
| Authorized client attachment / grants | Transport-specific verifier + interface admission | Bound to server, app/interface, version, runtime generation, principal and allowed operations; must be checked at dispatch |
| Operator command attempt / receipt | Authoritative process/control owner | Must identify target registration and exact launch attempt, preserve status and an *unknown outcome* when acknowledgments are lost |

No persistent registry, new schema file, wire message or public Rust type is implied by this conceptual matrix. The binding among a build, Manager registration and running app must be verified, not inferred from the same name or endpoint.

### 2.2 Observations are scoped facts, not one misleading linear “ready” state

Report each applicable independently observable fact with **subject, observer/authority, generation or launch attempt, evidence, observed-at time and freshness**; stale or absent observations are *unknown*. Examples:

- Authored definition known / validated runtime plan. Reading a verified artifact is passive; executing an app for `--print-definition` runs trusted Rust setup, and Cargo builds execute build scripts.
- OS process accepted/start/alive, plus owner reconciliation; *not* provider or application readiness.
- Required provider handshake ready; *not* app handler or exported interface readiness.
- Application handler initialized; published interface bound; **specific authenticated interface callable**, established by permitted endpoint-level evidence.
- Failed, degraded, disconnected, stopped, unauthorized and indeterminate observations remain distinguishable. Facts can be revoked and different interfaces may be at different stages simultaneously.

Never promote a socket bind, PID, port, `RIESEL_READY`, `TODO_HTTP_READY` or successful binary inspection into an authenticated callable guarantee. A read-only inspector may show weaker evidence clearly labelled rather than fabricate stronger guarantees.

### 2.3 Session fencing and lifecycle

The real whole-application session is the source of an externally conveyed fresh generation. Publication/withdrawal of the interface is coupled to runtime startup, revocation and teardown. Admission checks expected generation and currently authorized grants **before dispatch**. An attachment from an earlier generation is never transparently rebound to a new session, even when PID, address or OS process does not change. Closing a GUI does not stop an app. Revocation prevents *new admission*; operations already dispatched may finish or have uncertain side effects and must be accounted for. Research-only synchronous locking in #95 is **not** an acceptable async blocking-shutdown guarantee.

### 2.4 Trust, authentication, authorization — an explicit fork in policy

An identity assertion, version match, loopback bind, Unix socket file permission or `SO_PEERCRED` UID is not sufficient to distinguish two hostile processes running as the **same UID**. Different protections are required for:

- **Trusted local developer profile (candidate):** every same-UID participant is explicitly assumed trusted, only deliberately opt-in low-privilege interfaces are permitted, and UI/docs disclose the absence of hostile-same-UID isolation. This profile must never be described as an authorization mechanism protecting privileged Manager control.
- **Protected local control profile (candidate):** a separately protected OS principal/service or equivalent proven confinement/broker has authority for sensitive operations; the caller verifies server authority, and the server verifies caller identity and granular grants. Cross-platform equivalents require their own tests. If no defensible boundary exists, refuse protected operations rather than silently downgrade.
- **Remote profile:** separate future specification for authenticated/encrypted transport, credentials and secrets; no automatic promotion of today's plaintext loopback RPC.

**Owner decision accepted 2026-11-21 (choice B):** privileged Manager commands **must resist untrusted same-UID processes**. A protected, verified control/OS authority boundary is therefore mandatory before shipping writable Manager control; fail closed where it is unavailable. A trusted-local development/read-only profile may be separately defined but cannot claim this protected requirement. This decision chooses **the security goal only**; service identity, confinement/broker, OS adapter, public auth/IPC mechanism and protected-GUI details remain open. See [#59 decision](https://github.com/aschenrot/riesel/issues/59#issuecomment-7062536105) and [#75 coordination](https://github.com/aschenrot/riesel/issues/75#issuecomment-7062536567).

### 2.5 Command and mutation outcomes

Distinguish at minimum:

1. **Rejected before dispatch**: invalid version, revoked generation, absent grant, malformed request, invalid configuration. No command was admitted under the checked boundary.
2. **Definitive application result**: success or typed domain failure when authoritative completion is known. Domain failure does not automatically imply no partial effects unless that domain contract provides atomicity.
3. **Outcome unknown after possible dispatch**: timeout, lost response, disconnect, owner/controller crash or revocation while an operation may be in flight. Do **not** report “failed without effects”, silently retry mutations or claim exactly-once delivery.
4. **Observational uncertainty**: the observer cannot establish current process/interface state or receipt; status is stale/unknown, not false “stopped/ready”.

Reattach only with a new verified current generation and grants, then obtain an **authoritative snapshot or command status** appropriate to the domain. Idempotency/durable command deduplication, event subscriptions and exactly-once results need separately specified durable authority; they are not generic transport flags.

## 3. Product specifications to accept, revise or defer separately

### #68 — Cross-project developer workflow

**Proposed decision: ACCEPT the two-layer boundary** as a technical direction: a thin, optional Cargo-aware foreground orchestrator reuses Cargo artifact discovery and an SDK/runtime-defined *participation* boundary. Ordinary headless `cargo` and app-scoped CLI remain valid; no second schema, dependency resolver, process supervisor, manifest, Manager, Node or frontend is mandatory. Do **not** accept public command spelling or SDK hooks yet.

**Proposed first implementation slices, after mechanism acceptance:**

- **T-A — independent Cargo foreground tooling.** Identify exact binary through Cargo JSON compiler-artifact records; distinguish passive artifact metadata from trusted executable inspection; run a headless app as a directly owned child; show build/app/handler exit and provenance separately; stop/reap only an owned child. No claims of universal graceful or descendant shutdown. Test a Cargo workspace outside the repository, missing targets/tools, duplicate targets, early exit and interruption.
- **T-B — opt-in interface/development adapter.** Accept app-declared static-asset/frontend participation without copying Todo-specific scripts. Require explicit stable SQLite/data paths initially; an OS state-dir default and precedence are a later decision. Verify dynamic application-interface readiness before opening a browser; independent browser close cannot stop the app; prove retained data across restart. No unannounced package install, hidden migration or silent temporary default data.
- **T-C — failure/portability hardening.** Reject false/oversized/stale readiness and ambiguous duplicate starts; bound output, timeout and cleanup. Define an app-owned cross-platform graceful-stop participation mechanism rather than assuming Todo SIGINT or managed-provider stdin applies universally; Windows stays an explicit manual release gate.

**Independent progress:** T-A's Cargo artifact/build and explicitly owned foreground child can be implemented without privileged #75 export or a Manager. General *authenticated interface* verification in T-B must consume #75 semantics rather than invent a launcher token. Do not call T-A blocked by completing #59 or #60.

**Remaining acceptance questions:** packaging/commands, minimal SDK participation, portable graceful stop, data-path precedence and whether first browser asset build is only explicit opt-in. See [#88 report](https://github.com/aschenrot/riesel/blob/research/68-cross-project-developer-workflow/research/developer-workflow/REPORT.md).

### #59 — Installed Manager and process ownership

**Proposed decision: ACCEPT for further specification** a single-host Manager control contract over explicitly trusted registrations; prefer a **hybrid with exactly one selected owner per attempt**. As the *first Linux engineering adapter*, real systemd user transient `.service` ownership plus durable registration/attempt admission is a research candidate, **not** authorization for a Linux-only first Manager release or proof of protected same-UID commands. The foreground direct-child development mode is distinct and must not silently substitute when systemd is unavailable. No platform-wide process-tree cleanup or automatic PID adoption claim.

**Owner decision accepted 2026-11-21 (choice A):** installed applications must **survive Manager controller process failure, restart or upgrade** while their own process and independent OS owner remain healthy. The returning controller must reconcile trusted durable registrations and the *same exact* OS launch attempt before permitting commands; it must not guess or adopt a PID, relaunch on an unknown outcome, or stop a new attempt with an old receipt. This is a **required lifecycle outcome**, not a selection of systemd, a broker or a permanent Manager process-owner mechanism. It is compatible with and does not weaken the [accepted protected-control requirement (choice B)](https://github.com/aschenrot/riesel/issues/59#issuecomment-7062536105). See the [owner decision in #59](https://github.com/aschenrot/riesel/issues/59#issuecomment-7062613324) and [#75 coordination](https://github.com/aschenrot/riesel/issues/75#issuecomment-7062613694). It does not set host-reboot, logout, OS service-owner failure, application-crash restart or auto-launch policy.

**Owner decision accepted 2026-11-21 (reboot startup choice A):** installed apps have an **individually configurable, durable OS-reboot startup policy**, defaulting to **manual**; opt-in automatic startup is allowed only when an authorized operator enables it for that registered application. On boot, the protected independent owner must reconcile trusted registration and any pre-existing OS launch attempt before starting; never duplicate, adopt guessed PIDs or silently replay uncertain commands. Disabling auto-start prevents future automatic boots but does not itself stop a currently running app. The exact Linux/Windows/macOS owner, before-login vs after-login timing, OS-owner availability and installation/authorization mechanism remain undecided. This is **not** a decision about restarting apps after their own crash. It must preserve previously accepted [same-UID-resilient privileged control](https://github.com/aschenrot/riesel/issues/59#issuecomment-7062536105) and [Manager-crash survival](https://github.com/aschenrot/riesel/issues/59#issuecomment-7062613324). Recorded in [#59](https://github.com/aschenrot/riesel/issues/59#issuecomment-7062650105) and coordinated in [#75](https://github.com/aschenrot/riesel/issues/75#issuecomment-7062650422).

**Owner decision accepted 2026-11-21 (process-crash recovery choice A):** each registered installed application has a **durable, independently configurable unexpected-process-crash restart policy**, **disabled by default**; opt-in recovery must have bounded retries, backoff and crash-loop protection. Deliberate Stop/clean exit cannot trigger recovery. A recovering process receives a fresh immutable OS launch attempt, while the Riesel runtime issues its own new session generation; stale external clients are not silently rebound. Manager controller crash during an attempted restart must reconcile any uncertain OS state before another launch; no uncontrolled duplicate or insecure same-UID write path. Retry-limit constants, healthy-runtime reset thresholds and platform implementation are **not selected**. This is independent of [reboot-startup opt-in](https://github.com/aschenrot/riesel/issues/59#issuecomment-7062650105) and existing in-process Riesel recovery. Recorded in [#59](https://github.com/aschenrot/riesel/issues/59#issuecomment-7062683971) and coordinated in [#75](https://github.com/aschenrot/riesel/issues/75#issuecomment-7062684320).

**Owner decision accepted 2026-11-21 (platform release option C, Linux-only routine CI):** the **first completed installed Manager release must support Linux, Windows and macOS**, each satisfying the same accepted security, lifecycle and operational guarantees. Platform adapters can be built incrementally, beginning with Linux, **but Linux-only implementation is not release complete**. **Routine PR/commit CI remains Linux-only** (`cargo validate --check`, `cargo smoke`). Windows remains a manual pre-release gate under [delivery.md](../../project/delivery.md); **macOS requires similarly documented manual checks for the Manager release**, on actual macOS against the release candidate. Cross-building or modeling another OS is insufficient evidence for OS-specific process control, protected same-UID authority, Manager death/reconciliation, reboot startup or crash-loop recovery. Failing/unavailable Windows/macOS evidence must prevent claiming the three-platform release ready. OS-specific mechanisms may differ, but core semantics and security cannot be weakened. This is a release scope and verification policy decision, **not** selection of a specific backend, installation model, or login/boot timing. See [#59 owner decision](https://github.com/aschenrot/riesel/issues/59#issuecomment-7062981420) and [#75 coordination](https://github.com/aschenrot/riesel/issues/75#issuecomment-7062981778).

**Owner decision accepted 2026-11-21 (execution scope choice A):** the installed Manager must support **both user-session applications and machine background services**, with a **durable explicit execution scope per registered application**. Scope determines the independently owned OS process and its sign-in/logout/boot behavior; neither implies the other is automatically installed or authorized. Across Linux, Windows and macOS, user-session and machine-wide services reuse one management identity/command/readiness vocabulary, but require **scope- and platform-appropriate protected OS authorities**, including authorized installation/elevation for machine services. A user-facing Manager GUI has no automatic machine-service mutation privilege; previously accepted **hostile-same-UID resistance** applies at both scopes. Machine services can operate without interactive login; user-session logout effects and exact boot/login timing need technical acceptance. Startup remains **manual after reboot by default** and process-crash auto-recovery remains **off by default** per app, with separate explicit opt-ins. Scope changes must be protected, deliberate, reconciled and observable; no unverified in-place PID adoption. This is first-release scope alongside three-platform parity, **not** selection of systemd user/system units, Windows service mechanism, launchd domain, broker, GUI or API. See [#59 decision](https://github.com/aschenrot/riesel/issues/59#issuecomment-7063052986) and [#75 coordination](https://github.com/aschenrot/riesel/issues/75#issuecomment-7063053415).

**Owner decision accepted 2026-11-21 (first Manager interface choice A):** the first installed Manager release must provide **both CLI and a local browser UI**, as clients of **one authoritative protected management contract/API** with shared application identity, exact attempt, readiness, command outcome and error semantics. Native Manager desktop UI is **not a first-release requirement** and may later use that same contract. Both clients require verified authorization for privileged operations, including denial of untrusted same-UID processes. A loopback listener, browser origin check or readable same-user bearer credential is **not sufficient**; the browser additionally requires origin/CSRF/session protections. A local GUI cannot bypass the protected process owner to control machine-scope services. Define the precise initial set of writable register/configure/start/stop/restart commands and installation/elevation UX before freezing a public API; do not replace CLI with a read-only browser or create two independent management implementations. The choice does **not** mandate HTTP or a particular auth/UI toolkit, and does not authorize remote control. Actual Linux + manual Windows/macOS interface/security tests remain release gates. See [#59 decision](https://github.com/aschenrot/riesel/issues/59#issuecomment-7063086806) and [#75 coordination](https://github.com/aschenrot/riesel/issues/75#issuecomment-7063087236).

**Owner decision accepted 2026-11-21 (application onboarding option C):** first-release Manager supports **both** secure registration of already available **trusted executables** and **Manager-owned installation, update and removal**. Both paths converge on one logical registration, independently verified executable/build provenance, immutable OS launch attempts, scope-specific protected authority and common CLI/browser management contract. Newly installed/updated executable content must be verified and protected against same-UID substitution or path-swap races before activation; the exact package format, provenance/signing trust anchors, source distribution/registry and updater mechanism are **not chosen**. Update/removal must be safely staged, guarded against concurrently running or stale attempts, and reconciled after controller crash/unknown command outcomes. Neither unverified in-place binary replacement nor implicit application data deletion is authorized. App compatibility, state migration/rollback, update automation, and removal-data retention policy are separate unresolved specification decisions. Both execution scopes and all three first-release OS targets are required. This expands #59's implementation research scope; do not claim a production installer. See [#59 owner decision](https://github.com/aschenrot/riesel/issues/59#issuecomment-7063129250) and [#75 coordination](https://github.com/aschenrot/riesel/issues/75#issuecomment-7063129682).

**Owner decision accepted 2026-11-21 (uninstall data choice B):** Manager **preserves persistent app data by default on uninstall**. An authorized operator may explicitly choose and confirm deleting **only positively verified, exclusively application-owned managed data**; shared, externally managed or unverified data is **never implicitly deleted**. CLI and browser must offer the same protected deliberate choice with **preserve preselected**, an exact data-scope preview, server-enforced authority and revalidation just before deletion; same-UID untrusted programs must not bypass this. Separate registration, installation artifacts, app runtime attempts and data ownership; never infer exclusive deletion rights from an app-provided path, same OS UID, symlink traversal or a guessed directory. Stop/reconcile the exact OS process owner and storage locks before deletion; mid-uninstall failure or lost response remains **partial/unknown**, with no automatic destructive replay. Reinstall may not silently overwrite retained data. This policy is **not** a claim of universal data discovery, reversible uninstall, guaranteed backup or secure erasure; inventory/provenance, storage path, transaction and backup details remain technical decisions. Verified user-session/machine-service behavior on Linux, Windows and macOS remains a first-release gate. Recorded in [#59](https://github.com/aschenrot/riesel/issues/59#issuecomment-7063212905) and [#75 coordination](https://github.com/aschenrot/riesel/issues/75#issuecomment-7063213273).

**Owner decision accepted 2026-11-21 (update policy choice A):** first-release Manager supports a **durable update policy per registered application: manual operator approval by default; automatic updates only after explicit per-app opt-in**. Opt-in authorizes **only verifiable, safe, compatible updates** from an explicitly trusted/approved update source; registering a separately built existing executable alone does not establish an automatic update feed. Enabling auto-start or crash recovery must not enable updates. Verification must cover artifact/content provenance and protected same-UID authority, prevent symlink/path substitution, keep immutable version/launch-attempt/runtime-session boundaries and distinguish downloaded/staged/installed/activated from actually callable readiness. If data compatibility, required offline migration safeguards or an authorized update transition cannot be established, **block automatic activation** and surface the reason; do not infer permission for destructive migration, unconditional rollback or zero downtime. For interrupted updates, record partially completed/unknown outcomes and reconcile before reattempting any mutation. CLI and browser expose the same policy, approvals and status. This is **not** a selection of registry, signatures, update cadence, rollback or maintenance-window mechanism. See [#59 owner decision](https://github.com/aschenrot/riesel/issues/59#issuecomment-7063269195) and [#75 coordination](https://github.com/aschenrot/riesel/issues/75#issuecomment-7063269621).

#### Manager owner-delegated conservative defaults (2026-11-21)

The owner asked to **continue autonomously with the recommended setup** rather than hold further repetitive product-choice rounds. The policies below were adopted under that *delegation*, **not** explicitly selected one by one and **not** evidence that an API, OS owner or installation mechanism is accepted. Full decision rationale and tests: [#59 delegated defaults](https://github.com/aschenrot/riesel/issues/59#issuecomment-7063335749); [#75 coordination](https://github.com/aschenrot/riesel/issues/75#issuecomment-7063336242).

| Decision area | Delegated safe product default | Technical boundary still open |
| --- | --- | --- |
| Failed update | Retain previous verified artifact; **automatically restore only if current data remains compatible and OS/operation state is reconciled**, else stop and require operator action | Proven data compatibility, uncertain effects, migration, rollback evidence |
| Automatic update vs disruption | Auto-update opt-in does **not** implicitly permit stopping/restarting a running app; stage safely, defer activation until stopped or separately authorized maintenance/restart policy | Verified application drain, OS owner, timing and approval |
| Update distribution/trust | No automatic registry/feed for manually registered executable; require explicitly approved source plus independently trusted artifact provenance before unattended updates | Source, trust anchor/signature, no same-UID path replacement |
| Scope at logout | User-session app is scoped to its login/session and may stop on logout; machine background service works without desktop login | Exact process owner and pre-login startup/install/credential semantics on each OS |
| Inspection and diagnostics | CLI/browser show app registration, installed version/provenance, desired policies, OS/process attempt and separate app/interface readiness, recent bounded sanitized failure/command evidence; passive inspection does not execute app code | Proven authority/freshness, secret redaction, portable diagnostic capture |
| Uncertain actions | Record completed / rejected / blocked / stale / partially completed / **unknown outcome** distinctly; reconcile before any action that may duplicate side effects | Durable receipt/journal, admission/fencing, no exactly-once assumption |
| Surface | Single-host protected CLI/browser in first release; no default remote control, public marketplace, fleet scheduling or arbitrary shell execution | Scope extension needs distinct acceptance |

**Next decision-critical evidence work (not selected mechanisms):** protected hostile-same-UID Manager authority on Linux/Windows/macOS in user-session and machine-service modes; independently verified OS owner/launch admission and real-Riesel controller crash reconciliation; trusted executable/update provenance without path substitution; app-level graceful-stop/data compatibility/rollback/removal inventory; common authenticated protected Management control for CLI/browser; and real Windows/macOS manual release checks beyond Linux CI. Do **not** claim the first Manager release is complete without these gates. Research and proposed implementation slicing may proceed, but no public wire/API schema, privileged daemon, crypto/registry format, merge or implementation milestone is approved by this delegation.

**New verified security counterexample — Gate M-S0 (2026-11-21):** [independent research PR #116](https://github.com/aschenrot/riesel/pull/116), [actual Ubuntu 24.04 CI 44910346787](https://github.com/aschenrot/riesel/actions/runs/44910346787), proved that an unprivileged **same-UID** process can directly send `SIGTERM` to its own-UID app process and stop it **without any Manager command**, while an otherwise equivalent different-UID unprivileged process is denied. Consequently, protecting **only Manager control IPC or registry** is insufficient for the [accepted hostile-same-UID guarantee](https://github.com/aschenrot/riesel/issues/59#issuecomment-7062536105) if the actual OS app owner remains an ordinary same-user process. A `systemd --user` transient service, same-UID file permissions, unit names and cooperative admission are insufficient as *complete protected Manager ownership* on their own. Research candidates include a protected OS authority **and** differently protected app/process principal, or genuinely OS-enforced confinement/security domain, with separately verified user-session GUI compatibility and legitimate authorized CLI/browser access. This is **negative evidence, not acceptance** of a broker, separate service account, sandbox, API or installation plan; Windows/macOS parity remains unverified. See [#59 detailed evidence](https://github.com/aschenrot/riesel/issues/59#issuecomment-7063549286).

**Executed machine-service process isolation and explicit operator-auth counterexample — Gates M-S1a / M-S2 (2026-11-21):** [independent research PR #123](https://github.com/aschenrot/riesel/pull/123) exercised a real **system-level** transient service running under a distinct `DynamicUser=yes` app OS principal. At `79e268155699c5fa2ef87f366a542cf73d30d711`, actual Ubuntu 24.04 [research CI 44912045311](https://github.com/aschenrot/riesel/actions/runs/44912045311) and [normal Linux Validate/smoke 44912045317](https://github.com/aschenrot/riesel/actions/runs/44912045317) both **PASSED**: the system-owned process survived controller death, and two independent clients **sharing unprivileged UID 60090** failed to send direct SIGTERM, execute systemd machine stop/restart/kill or modify an OS-protected registration fixture, without changing the service's `MainPID` or `InvocationID`. An extended fixture [research CI 44912513846](https://github.com/aschenrot/riesel/actions/runs/44912513846) **PASSED** at `d5a338f1c1ba6b4e011993af6ef3e13fda68fde3`: a **different unprivileged sibling program under the CI operator's own UID** could successfully use that account's **ambient passwordless sudo** to stop the same protected unit. Thus **OS target isolation** is a credible machine-scope candidate, while broad sudo or same-user elevation is **proven insufficient for genuine per-client authorization**. The later PR's normal Validate/smoke is an independent exact-head gate. No legitimate-vs-hostile same-UID CLI/browser admission, protected user-session GUI interoperability, durable installer/data path, safe launch fencing or Windows/macOS owner has yet been demonstrated. `DynamicUser` is a disposable fixture, **not an accepted installed Manager service identity**. The next decision-critical work remains M-S1b user-session interoperability and M-S2 protected per-operation authorization; no privileged daemon or public protocol has been accepted. See [#59](https://github.com/aschenrot/riesel/issues/59#issuecomment-7063817801), [#75](https://github.com/aschenrot/riesel/issues/75#issuecomment-7063818705) and PR #123's evidence/matched alternatives.

**Critical choice:** immutable **per-attempt** unit identity + durable transactional reservation is the safer current candidate than reusing one unit name and issuing a non-atomic check-then-`StopUnit` against `InvocationID`. Research observed that a stale name-only stop can kill a replacement and a unique per-attempt name prevents this *particular* error but allows duplicates unless an independent durable registration gate exists. SQLite reservation and systemd activation are **not one transaction**: preserve unresolved launch as unknown and reconcile the exact recorded attempt rather than retrying automatically. Neither invariant protects against a privileged or same-UID actor able to bypass the controller and edit registry/OS services.

**Proposed implementation slices after trust/owner specification acceptance:**

- **M-A — secure registration, artifact provenance and admission:** authorize and verify both externally prepared trusted executables and Manager-installed artifacts under one registration/identity model; guard verified binary/version/config paths against substitution and executable race; immutable OS launch-attempt identity, competing-controller serialized admission, revocation/unknown-state record and no-duplicate semantics under the accepted actor model. No arbitrary PID adoption.
- **M-B — Linux OS ownership adapter and protected-principal comparator:** actual OS-owned service start/observe/stop for the recorded attempt, crash reconciliation, delayed-start/stop races, unavailable manager and verifiable app-level stop. [#99](https://github.com/aschenrot/riesel/pull/99) **passed** a bounded genuine Riesel Todo + linked SQLite systemd-user service exercise in [Linux CI 44910721418](https://github.com/aschenrot/riesel/actions/runs/44910721418): process survived controller death, actual HTTP callability separate from OS state, persistence through a new immutable OS attempt and stale-stop isolation. **Normal app exit cause/graceful drain is not attested** because the transient unit returned `ExecMainCode=0`. As [#116](https://github.com/aschenrot/riesel/pull/116) shows, the tested same-UID user service **cannot** be promoted as a protected first-release Manager owner without additional independently proven OS process and caller isolation.
- **M-C — first-release CLI and local browser management clients over one protected contract:** both expose the accepted management workflows, list/inspect/status/diagnostics and the authorized first-release control subset with shared command identity, stale-attempt fencing, unknown outcomes and truthful process versus interface readiness. Browser writes cannot ship until real same-UID-resistant server/OS-owner authority, per-command permissions and browser origin/CSRF/session protections are proven; read-only browser is not a substitute for the accepted first-release UI. Native Manager desktop UI can follow. Framework/transport choice is separate.
- **M-D — Windows/macOS and user-session/machine-service owner adapters + manual release evidence (required for first Manager release):** implement equivalent authorized OS ownership/control and application lifecycle/recovery semantics on Linux, Windows and macOS in **both explicitly selected scopes**, including secure scope admission/elevation, machine service without sign-in and defined user-session logout behavior; capture real Windows and macOS manual integration evidence for the release candidate. Linux is the only routine CI target. No Linux proof, cross-compilation or untested platform stub establishes parity.
- **M-E — first-release managed installation, update and removal:** evaluate/reuse credible OS installation and portable artifact mechanisms before freezing formats; implement protected artifact staging, integrity/provenance, safe version activation, guarded stopping and reconciliation, explicit partial/unknown results and deletion boundaries. **Per-app updates default to manual approval; opt-in automatic updates** require verified authorized source/provenance, executable path-swap resistance, compatible safe activation and explicit blocked/unknown state for unsafe data transitions or incomplete operations. Independently registered executables have no inferred automatic update source. **Uninstall preserves persistent data by default**; CLI/browser can delete only a positively verified exclusive app-managed data inventory through explicit protected choice, preview, confirmation and ownership recheck. Shared/external/uncertain data is never implicitly removed. Verify stateful update and uninstall failures, retained data and non-replay of uncertain destructive steps. No automatic migration, online catalog, zero downtime, secure-wipe or unconditional rollback claims. Required for release on Linux, Windows and macOS.

**Independent progress:** Manager process start/stop and registered-attempt fencing derive authority from the trusted OS owner and Manager registry, **not** from an app's exported capability or Riesel runtime generation. Manager can report OS-owned application status while callable app-interface status remains unknown. The #75 shared identity/error vocabulary is reused, not a requirement for one protocol or daemon.

**Remaining acceptance questions:** protected-control implementation enforcing the already accepted hostile-same-UID threat model on **Linux, Windows and macOS**; independently durable OS owner mechanisms, registration admission across OS calls, safe post-crash reconciliation, stop/receipt semantics, durable command journal semantics and portable Riesel graceful stop. Release readiness requires actual OS-specific manual proof beyond the Linux CI baseline. A Manager UI does **not** depend on a native #60 host. See [#94 report](https://github.com/aschenrot/riesel/blob/research/59-systemd-user-owner-probe/research/process-ownership/systemd-user-service-report.md).

## 6. Protected-control proof gate M-S2 (research proposal, not architecture acceptance)

**Outcome:** #59 and #75 require an authorized CLI or local-browser request to perform one specifically authorized privileged Manager operation while an independent hostile **same-OS-user** process cannot cause that operation. PRs #116, #123, #129 and #134 established critical process-ownership and negative evidence, **not** this guarantee. Independently published #60 app capabilities require separate explicit trust/authorization decisions.

**Test adversaries and assumptions:** Include same-user processes that can invoke a trusted executable, read ordinary user files, use localhost, influence X11 desktop input and exercise any actually delegated elevation permissions; separate them from OS-protected app principals, protected command owners and trusted authorization mechanisms. A process able to obtain unrestricted root/administrator/kernel authority can bypass ordinary OS process isolation; deployments with such effective authority available to attackers cannot claim this guarantee. Verify whether the attacker is confined or unconfined and whether any untrusted actor can enter or impersonate a trusted client security domain. Do not assume Wayland or mutually isolated Xwayland clients.

**Compare credible architectures on the same accepted outcome:** (A) separately OS-protected mutation broker with exact-action trusted approval or narrowly preapproved unattended policies; (B) mandatory nonforgeable OS client domains plus independent operator authorization/policy; (C) relevant native OS privilege and consent mechanisms with constrained CLI/browser adapters. A peer UID, signed binary, security label, local socket permission, same-user bearer secret, browser session or protected OS owner **alone** does not pass.

| Gate | Positive evidence and required hostile negative cases |
| --- | --- |
| M-S2.1 Exact permission | An intended operator approves the precise logical registration, immutable OS launch attempt, action, parameters and bounded validity; the broker, not an attacker-controlled name/path/PID, resolves authority. Wrong app, verb or target is denied **before OS mutation admission**. |
| M-S2.2 Same-user attacker | A separate same-UID process attempts direct API/IPC and browser writes, launches the genuine protected CLI, uses ordinary code injection where possible, and replays requests. Without independent authorization no protected mutation occurs; record actual OS/domain credentials, not client claims. |
| M-S2.3 Stale/replay/race | Test wrong session/attempt, expired authorization, copy of an observed approval, parallel redemption by two callers, controller restart and privileged server substitution. An approval is not reusable for another operation, attempt or actor. |
| M-S2.4 OS bypass | Attempt direct signals, process/service manager commands, registry/executable substitution and broad ambient sudo. Denials leave the actual app PID and immutable attempt unchanged. Authorized stop affects the exact attempt, not a later replacement. |
| M-S2.5 CLI and browser | Both use the same broker and command outcome. Test Host/Origin, CSRF, malicious local requests and programmatically influenced UI input. A web page click is not proof of a protected human decision. Replay the real X11 input-injection case from PR #134; if the available consent path can be spoofed, privileged requests must fail closed. |
| M-S2.6 Unattended policy | Separately authorized, durable, server-owned per-app policy enables only its declared reboot/crash/update transitions and limits. It cannot silently authorize other apps, upgrades, attempts or destructive changes; revocation is enforced. |
| M-S2.7 Unknown result | Force controller death, lost reply, revocation during dispatch and duplicated commands. Preserve actual state/receipts and distinguish completed, rejected, partial and unknown; never infer nonexecution or blindly replay destructive operations. |
| M-S2.8 Independent GUI | Test app-export grants/stale runtime generations and unapproved second GUI access **separately**; no app-facing grant may elevate to Manager authority. An unauthenticated Counter attach from PR #134 remains a negative baseline. |

**Platform-specific candidate checks, not selected mechanisms:**

- **Linux:** polkit has distinct mechanism, authority and authentication-agent roles; the tested username-based YES rule in PR #123 admitted both same-UID clients. Its documented AUTH_SELF_KEEP and AUTH_ADMIN_KEEP reuse for the same action identifier can allow later checks **despite different action details**; do not treat cached elevation as exact registration/attempt authorization. Test a real trusted approval path, detail binding and absence of unsafe temporary grants. The AppArmor proof in PR #129 worked only when the attacker could not self-enter the trusted profile. The PR #134 X11 attack and non-isolated Xwayland clients constrain input trust. Sources: [polkit rules](https://polkit.pages.freedesktop.org/polkit/polkit.8.html), [polkit authority](https://www.freedesktop.org/software/polkit/docs/latest/polkit.8.html), [Xwayland](https://wayland.freedesktop.org/docs/book/Xwayland.html).
- **Windows:** compare Windows service/process principals, secure IPC and per-operation trusted approval (potentially UAC secure desktop). A named-pipe/RPC caller security token identifies an OS identity, **not independently the intent** of two same-user processes. Sources: [UAC](https://learn.microsoft.com/windows/security/identity-protection/user-account-control/how-user-account-control-works), [pipe access](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights), [client impersonation](https://learn.microsoft.com/en-us/windows/win32/secauthz/client-impersonation).
- **macOS:** compare launchd/Service Management installed helpers, XPC isolation and independently authorized privileged action. Do not use deprecated AuthorizationExecuteWithPrivileges as a new design. Sources: [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice), [Service Management](https://developer.apple.com/documentation/servicemanagement), [deprecated API](https://developer.apple.com/documentation/security/authorizationexecutewithprivileges).

**Research execution/stop rule:** First state each candidate's protected authority, input trust and OS privilege assumptions. Next produce one *legitimate succeeds / hostile same-UID fails* exact-action pair on a real Linux OS-owned Riesel app, including direct OS bypass. Only then test browser/GUI input, replay/race, policy and uncertain dispatch. Actual Windows and macOS manual verification in **both** Manager execution scopes remains mandatory before the first complete release; routine CI remains Linux-only. Each experiment must record reproducible steps, exact revision, OS/session identity, observed process/command state, negative cases and cleanup. Do not run more UID/executable/label-only experiments unless they could change the architecture choice. An untrusted graphical/input deployment without a trustworthy authorization path is **unsupported for protected mutation**; do not silently downgrade the first-release promise. No broker, external protocol, credentials, OS adapter or implementation Issue is accepted by this annex.

### 6.1 Executed protected-control subgates and remaining architecture choice (2026-11-22)

The first M-S2 experiments now establish **separate** facts; combining them into a complete first-release Manager guarantee is still unproven. Each finding is tied to a tested source revision, not to an accepted implementation:

| Verified experiment | Real tested observation | What remains unproven |
| --- | --- | --- |

**Critical interpretation:** Root ownership, OS/PAM credential verification, action-detail checks, and a familiar browser/desktop prompt are **four different trust claims**. They cannot be conflated. The tests specifically falsify “a cached elevation refers only to the approved target” and “the final X11 confirmation event necessarily came from the actual operator.” The attacker does not need to know the generated test password to contribute the final X11 event in that bounded fixture; the password was entered by the legitimate test driver beforehand. The desktop account in that X11 fixture also had CI-wide sudo, so it is **not** a test of protection against unrestricted same-user escalation.

**Candidate trust profiles to investigate — not accepted backend choices:**

- **Interactive trusted approval:** An OS-protected authority must present (or otherwise independently attest) an immutable registration/attempt/action/options to an operator through a **verified nonspoofable approval channel**, whose trust is demonstrated against the actual same-user desktop/browser adversary. Authentication with ordinary X11 input alone does not provide that proof; ordinary polkit credential success is insufficient. A platform-specific protected authorization surface is permissible, but do not infer it exists on every Linux desktop.
- **Bounded unattended policy:** The protected owner may execute only a separately approved, durable, revocable per-app automatic policy with explicit scopes (boot/restart/update/etc.), deadlines, provenance and crash/rollback limits. Policy **issuance or modification** itself requires a trusted authorization path; a mutable user-file/CLI flag does not suffice. No implied destructive mutation permission.
- **Unsupported input/ownership environment:** On a session with spoofable trusted UI or same-UID direct owner bypass, privileged Manager mutation must fail closed or the deployment must be labeled **outside the accepted protected profile**. The Manager UI may still expose nonprivileged read-only status; unprotected actions cannot be relabeled as protected. A secure user-session application owner remains a separate blocking investigation, not solved by machine-scope systemd results.

**Next decisive research, not more copies of prior probes:** Exercise **one real Linux Riesel registered application and exact OS invocation** with a _legitimate_ protected CLI/browser-initiated approval and _hostile same-UID_ attempts to initiate, redirect, inject into or replay it. Verify no ambient sudo, X11/UI-origin bypass or forged agent; either demonstrate a trusted OS/session authorization path or document supported-environment restrictions.
