# Application-owned T1 read publication — first SDK policy slice

**Status:** opt-in implementation in progress under [#258](https://github.com/aschenrot/riesel/issues/258). The feature `app-publication` provides the **read-only policy/admission core**, not a completed independent GUI connection, endpoint identity verifier, transport, protected caller authentication or product release.

## Accepted architecture

[Owner-accepted P3 + T1](operational-contract.md) permits an application to deliberately publish selected versioned app-facing read models for independent GUIs. The first local profile explicitly assumes programs running under the same OS user are trusted, and the exposed data is non-sensitive. It does **not** protect against malicious same-UID processes, a counterfeited socket endpoint, private data access or hostile unapproved GUI clients. Stronger client/server identity and operation grants remain separate work for sensitive observations or mutations. Riesel's runtime generation is a **nonsecret session fence**, not a credential.

## Core authoring

With `riesel` feature `app-publication`, an application owning a `RunningApp` may call:

```rust,ignore
// A deliberate app-owned facade generated by #[capability] can supply
// an AsyncRpcHandler. Only "snapshot" is selected for publication.
let read = running.publish_local_reads(
    "example.riesel_app",
    "execution_graph_view",
    riesel::ReadExposure::NonSensitiveSharedUser,
    generated_app_read_dispatcher,
    ["snapshot".to_owned()],
)?;
let description = read.descriptor(); // not server authentication
let snapshot = read.query(&description, "snapshot", serde_json::json!({})).await?;
```

The SDK's `Context::publish_local_reads` offers the same path inside a running application callback. The handler must implement the **existing versioned `AsyncRpcHandler`** contract; no duplicate query schema or second provider resolver is created. Only `OperationKind::Query` entries explicitly listed by the application are admitted. A `Command` kind is rejected **at publication construction**. A client requesting an unselected operation, other contract/version/application or stale generation is rejected before domain dispatch. App withdrawal and runtime ingress share a pre-dispatch admission fence; a permitted in-flight read may finish after withdrawal, but old runtime sessions do not become current on restart. A bounded request/response and runtime in-flight capacity prevent unbounded policy-core allocations.

This function does **not** open a port, bind to a Unix socket, launch a GUI, create a registration, verify peer credentials, or establish a trusted server endpoint. `query` is callable within the application/adapter process; any independently operated client still needs a separately verified T1 local transport adapter enforcing its declared scope and browser-origin policy. Do not send a `ReadPublicationDescriptor` to an arbitrary remote endpoint and treat the returned strings as authoritative identity. Only the application can attest whether the selected data is non-sensitive; Riesel cannot infer this from a read-only method name.

## Optional Unix-native independent client (T1 local only)

With features `app-publication-unix` and a Unix-like OS, the application can
bind an **explicit absolute socket path** using `UnixReadServer::bind(path)`,
and serve an `Arc<AppReadPublication>` using
`UnixReadServer::serve(publication).await`. Run that future as a named
`AsyncTasks::spawn` task in the application's active SDK async entrypoint;
there is **no daemon, hardcoded global port, Manager registration or UI
renderer**. The server's socket is created mode `0600` and cleaned up
only when the on-disk inode still matches the server's original endpoint.
Use a private trusted local directory (for example mode `0700`) and
disclose its path through an **application-owned trusted launch/discovery
channel**. The path and returned fields alone are not authenticated server
identity against other same-UID software.

A separate native program can use `UnixReadClient::new(path)`, then
`describe().await` for a **non-secret** published descriptor and
`query(&descriptor, "snapshot", args).await`. This first wire adapter
uses a versioned, bounded one-request/one-response JSON envelope and
has no subscriptions or implicit reconnect. An expired descriptor is
rejected; callers must obtain a fresh descriptor and authoritative
domain snapshot after session replacement. Successful replies and
typed error *codes* are exposed as JSON values. A UI must not
reinterpret missing/expired data as current and must not automatically
retry mutations (which T1 cannot publish in any case).

The local Unix adapter intentionally **does not** authenticate
individual same-UID processes, protect against a counterfeit endpoint
after unlink/rebind or serve browser clients directly; browser same-origin
security and cross-platform native adapters remain separately verified
work. The current implementation restricts to explicitly selected
non-sensitive `OperationKind::Query` methods, 16 concurrent client
slots, bounded request/response bytes and finite I/O timeouts.
Those are **initial adapter budgets**, not a benchmark or general
performance guarantee. The actual OS-process test verifies attach,
client detach/reopen, forbidden command rejection, app-session restart
and stale descriptor fencing through this SDK policy.

## Remaining #258 work

The optional Unix client is the first external adapter; still verify equivalent Counter, Todo and graph **app-owned** read models on one published policy across supported client hosts. Verify owned listener/task lifetime and bounded multiple clients, actual runtime restart and withdrawal, authoritative trace-loss resynchronization, documented same-UID/server-impersonation threat limits and exact full-workspace CI. A frontend remains optional and independently selected under [#114](https://github.com/aschenrot/riesel/issues/114). No T1 external mutations, sensitive data, graph controls, S2 plan publication or activation are authorized. Do not call the foundation complete based on policy unit tests alone.


## Read-only execution-graph facade (P3/T1 increment)

With the SDK feature `app-publication`, an app may opt in to the generated
`ExecutionGraphRead` version 1 contract
(`riesel.execution.graph_read@1`). An
`ExecutionGraphReadFacade::new(&validated_plan, runner.observer())`
requires the validated immutable plan's id/revision to match the real
authoritative graph run. Apps explicitly publish only `snapshot` and
`changes` through `RunningApp::publish_local_reads`; the GUI cannot
obtain the runner, controller or scheduler through this facade.

`snapshot` exposes plan/run/session identity, current phase, the
validated node dependency/binding/trigger declarations and authoritative
per-operation state/attempt, error and confirmed-effect prefixes. This
application-declared graph data must still be classified **non-sensitive**
before publishing it under T1. There is **no layout revision** in this
graph-only projection; a GUI must maintain separate presentation state
rather than synthesizing a semantic revision.

`changes(session_generation, run_sequence, cursor)` requires the exact
run address and returns a bounded retained transition list tagged with
that same identity. If `truncated=true`, the returned events are
deliberately empty: the client **must** call `snapshot` again and use
its `latest_sequence` as the new cursor. A future cursor returns a
typed `FutureCursor` error; an incompatible run returns
`StaleRun`. A snapshot and a separately read event slice are not one
atomic transaction, so clients need to handle loss/resync when reading
changes concurrently. Any unavailable or expired adapter/session is
**not** a completed or failed operation.

The graph facade imposes a 256-node maximum per published read surface
to bound this initial view; the underlying Riesel execution runtime is
not limited to that number by the facade. The shared publication
transport independently bounds serialized request/response sizes, so
an exceptionally large error string/prefix collection can still
return `over_budget` rather than expose a partial payload. This is
not a generic typed edge, nested-domain, GPU or editor document
format. App-specific domain views remain independent and separately
versioned.

On Unix, the separately selected `app-publication-unix` feature
allows the **same** generated graph read dispatcher to be served to
independent native client processes by `UnixReadServer` and
`UnixReadClient`, owned by the headless application's
`AsyncTasks`. The end-to-end process fixture verifies an actual
80-operation validated dependency graph, a child-process read-only
client, disallowed graph-control operation, real retained-trace
overflow/resnapshot, stale run/cursor and same-PID runtime restart.
This is a **native read client**, not a finished graphical inspector,
browser bridge, portable OS attachment or protected application-server
authentication. The first GUI is tracked in [#114](https://github.com/aschenrot/riesel/issues/114);
the remaining shared Counter/Todo read-model and lifecycle acceptance
work is [#258](https://github.com/aschenrot/riesel/issues/258).

## Counter and Todo application-domain read facades (T1 examples)

The generated graph read interface is not an exception to the shared
publication contract. The **actual** Counter and Todo applications also
deliberately select bounded, non-sensitive read facades under the same
`RunningApp`/`Context::publish_local_reads`, `ReadExposure` and
`UnixReadServer`/independent `UnixReadClient` semantics.

- **Counter:** the optional `riesel_counter_example` feature
  `t1-public-read` exposes `riesel.counter.public_value@1`
  `snapshot` only. It delegates through the **real SDK-selected
  Counter provider**, so application-owned `CounterContract::add`
  changes are subsequently visible; `add` and `label` cannot be called
  through this T1 read publication. Linux process tests use two genuine
  OS processes and verify contract-version fences and withdrawal.
- **Todo:** optional `todo` feature `t1-public-read` publishes
  `riesel.todo.public_summary@1` `snapshot` only. The facade reads
  a single bounded first page (maximum 32) through the actual registered
  Todo `Records<TaskData>`/Storage provider. It exposes only the page's
  open/completed counts, number inspected and `more_available`. It
  does **not** reveal titles, task IDs, revisions, records, arbitrary
  Storage/Query operations, or write commands. These are **not global
  totals** if `more_available` is true. The real-process regression
  verifies the app's private records remain absent from wire output
  and owner-only state changes are visible on the next read.

For a fully isolated, ephemeral and expressly non-sensitive Todo
fixture on Unix:

```sh
cargo run --locked -p todo --features t1-public-read --bin todo_t1_read_host -- 45
```

The app prints `TODO_T1_SOCKET=/absolute/local/path`. A separate
native T1 client can use `UnixReadClient::new` with that exact path.
No Todo CLI or local browser HTTP route is replaced or automatically
enrolled; the reference Counter and Todo publication features remain
**off by default**. Even task counts can be sensitive outside this
deliberately non-sensitive demo; a real user-data Todo application
requires its own classification and stronger separately authorized
profile before exporting private information. T1's trusted-same-user
assumption remains unchanged.
